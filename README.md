# Neru's 206 Dashboard

> **最后更新：2026-10-17** —— 下面的「最近进展」按日期倒序；每条只写发生了什么，**原始数字全在 `ACCEPTANCE.md`**（按日期可查）。要"现在到底在哪一步"，看 `docs/SESSION-STATE.md`（那一页每轮收工重写，比本文更贴近当下）。

2001 年 11 月的 206 CC MUX、自动挡、白底积家，原表仓里塞两块圆屏：左屏转速 + 水温，右屏车速 + 进气温度，表盘中间的表情代替指针。**原表继续通电**，挡位和警告灯仍由它负责 —— 这套屏只多看一眼车在干什么，摘掉它车照常开。总线是 K 线 + VAN（AEE2001），不是 CAN。

| | 左屏 · 转速表 | 右屏 · 速度表 |
|---|---|---|
| 外圈（缺口朝下） | 转速弧，刻度到 7000 | 车速弧，刻度到 210 |
| 内圈（缺口朝上、镜像） | 水温弧 | 进气温度弧 |
| 表情 | 只看转速，5 档：怠速 / 巡航 / 运动 / 高转 / 红区（5500 起，5580 进） | 只看车速，5 档：静止 / 市区 / 快速路 / 高速 / 超速（>130 进、127 退） |

水温、进气温度只驱动弧和数字，不换脸。红区按实测断油 6300 提前到 **5500**（2026-10-15 车主定），和表盘上限 7000 刻意分开。**弧与数字变红**走的是告警层那套阈值（转速 ≥ 5500、车速 ≥ 150，带 3 km/h 迟滞，可用 `theme.json` 的 `alerts` 段改），比表情的"超速脸"更晚一点 —— 表情是情绪层，红弧是告警色，两层刻意不同。弧与数字的颜色、几何、量程放在 `lib/themetool/ui_theme.h` 和运行时主题里，换配色刷 16KB 的 `theme` 分区即可，固件不用重编。

数据三路：转速 / 水温 / 进气温度走 K 线 OBD（ELM327，PID `010C` / `0105` / `010F`），车速 `Van > Obd(010D) > Sim`。K 线是排队共享的窄管子，每多一个时隙其余字段就慢 ~25%，所以转速和车速每轮都问、温度每 4 轮问一次；哪个源超过 3 秒没有新数据就退到下一档，断线只是那一格回到假数据，不黑屏。

VAN **不在 OBD 座上**：线号 9004 / 9005，优先从组合仪表插头取（反正要拆表），收发器 SN65HVD230 板上 120Ω 必须拆掉。手机蓝牙 ELM327 只用来上车前体检 —— 地库里松刹车、车挪不到一米车速就跟着变，说明那一路来自车轮转速传感器而不是 GPS；S3 没有经典蓝牙 SPP，车上仍是 USB 有线 ELM。

## 现在到哪一步

**两块 2.8C 已经在手上并跑起来了**：微雪 ESP32-S3-LCD-2.8C（非触摸，480×480 RGB 并口，RGB565），一块当**主板**（右屏 / 车速+进气）、一块当**从板**（左屏 / 转速+水温），各自插自己的 `USB` 口供电与看日志，**两板之间一根线都没有**。显示侧已定案：**PCLK 12 MHz**、双 framebuffer、弹跳缓冲 **30 行**（源文件默认 30，两个 `-now` env 也写 30；10 行那档肉眼可见横纹，见 `ACCEPTANCE.md`）、16 行绘制缓冲；主循环实测 ~1.4~2.3 万圈/秒。
★ 横纹那条历史口径：2026-09-27 的 A/B 是"20 行没横纹 / 10 行有横纹"，之后为车上留余量再调到 **30**；PCLK 也从 18 → 15 → **12 MHz**（降的是面板消耗速率，换的是 vsync ≈43/s）。**两个数都以源码/`platformio.ini` 为准，别信旧文档**。

板间链路已从"有线 UART"改为**无线 ESP-NOW 为主**（有线那一档**停用但一行不删**，见 `ARCHITECTURE.md` §8.3）：两块板同信道 6、不连 AP、`WIFI_PS_NONE`，地址自配置（广播 HELLO → 学到对端 MAC → 转单播 → 存 NVS）。

**链路已达标**（契约 §4 + `link_meas.h` 的三个门限全部通过，且持续负载下稳定）：最新一轮 10 次 burst 实测 **丢包 0.00%（门限 0.1%）、`gap_max` 13~20ms（门限 100）、p99 13~14ms（门限 20）、`over95`=0、样本 2000（≥300）**，从板 `locked` 52/52，面板 `timeout=0`/`fullrb=0`。

做到这一步靠的是把三处**"我们自己的"管道缺陷**逐个拔掉（**空中本身只占约 12ms**）：① 分发路径把整帧丢进局部变量（`LinkRx::feed()` 会把凑齐的帧交出来）—— 实测主板实发 199 帧/秒、从板只收到 ~6% 的 TICK；② **TICK 的发送**搬进高优先级任务（主循环被抢占不再拖住它），从板 TICK **3.8/s → 50.0/s**、`miss` 增量 **3531 → 0**、`tick_age` p95 **483ms → 19ms**、持续负载下 `locked` **30% → 100%**；③ 测量帧的**到达时间戳**搬进射频回调（原来在主循环里打，把收端抢占算进了到达间隔）—— `gap_max` **113ms → 22ms**、p99 **42ms → 14ms**。调度类改动只有眼睛能判，因此每一步都请车主在持续负载下看过屏幕确认**横纹没有回来**。

VAN 协议已经解完并在真实抓包上验过：帧布局（SOF 10 槽 / IDEN 15 位 / CMD 5 位）、FCS（`crc15_van_iso`，0x0F9D / init 0x7FFF / 取反 / MSB-first，覆盖 IDEN+CMD+DATA）、槽时间（**8.25µs**，规范标称的 8.00µs 偏 3.1%，已作废）都有抓包支撑 —— 怠速 1704/1704 帧、行驶 34051/34051 帧 FCS 全中。

- **转速已标定**：0x824 的 `data[0..1]`，16 位大端 ÷8。点火瞬间 raw 从恒 0 跳到 6152（= 769 rpm，起动机拖动），怠速平台 453 帧均值 7237.6（= 904.7 rpm，sd 26.9），地面真值 900 rpm，偏差 0.52%。
- **车速字段与绝对刻度都已定案**：0x824 的 `data[2]`，单字节，`kSpeedScale = 2.56`（1 计数 = 2.56 km/h）—— 真值源是蓝牙 ELM327 的 `010D`，双串口同源时间戳对齐后回归（368.2 s 行驶、599 个真值样本、284 对非零样本 R² = 0.9984）；数据可分辨范围 **2.55~2.57**，**2.56 是取整**。原始数据 `tools/serial-capture/drive-2026-09-22-van.csv` + `-obd.csv`，证据见 `VAN-PROTOCOL.md` 的「车速」一节。**旧口径「1 计数 = 1 km/h」已作废**（实测差 2.5 倍）。**四段定速标定跑仍按车主决定不做**。
- **已解字段接进了数据层**：`0x4FC` 的灯位域（左/右/双闪/近光/仪表盘灯）、门信号、`0xE24` 的 VIN。**没有**在 VAN 上的：刹车、雨刮、远光闪 —— 这三条别指望 VAN。

**软件侧已经不欠账了**：显示、双板链路、VAN 解帧与转发、BLE OBD、告警与诊断页、主题（配色 + 图片）编辑器、PC 客户端（`tools/app/dist/206Dash-Workbench.exe`，双击开真原生窗口）**都已收口**，车主在客户端里实机走完全程。**下一阶段不在代码里**：三维支架建模 → 上车安装（见下面「下一步」）。

还没做完的：VAN 上的油量/门灯细项、从板 SD 卡记录、表仓里的最终结构件（车主在做）、轮上第三块板（`docs/WHEEL-REMOTE.md`，等价格与尺寸）、素材还差两张脸。

**验证用的板子（历史）**：微雪 ESP32-S3-DualEye-Touch-LCD-1.28（240×240 GC9A01A ×2）已完成"真屏 240 档"验证并于 **2026-09-22 退货**。**240 档的结论不作废**：`esp32s3-spi` 环境、`ui_theme.h` 的 240 字号档、`tools/theme-editor/spec-240.json` 都保留且仍可编译，只是现在手上没有这块硬件。它的 ES8311 / 功放 / 喇叭座也随之不在手上。

## 编译 / 测试 / 刷机

仓库路径里有中文，ESP32 工具链会在中文路径下报 `g++ Invalid argument`，所以**构建在纯 ASCII 副本上做**，两边用 robocopy 同步；本机的 PlatformIO Core 和工作区依赖都不在系统 python 里，`PYTHONPATH` 与 `PLATFORMIO_CORE_DIR` 两个环境变量不能省（宿主机编译器是 **`C:\206dash-scratch\zigbin`** 里的 zig 转发桩：`gcc.cmd` / `g++.cmd` → `C:\ziglang\zig.exe cc`；**仓库里的 `.tools\zigbin` 不存在**，`C:\mingw64` 也不存在）。不走 `tools\build\pio.ps1` 手搓 pio 时，下面每一行都在 `$copy` 目录里执行。

```powershell
$repo='C:\Users\张九思\206Dash\Neru-s-206-dashboard'
$copy='C:\206dash-scratch\now'
robocopy $repo $copy /E /XD .git .pio /NJH /NJS /NP      # 退出码 1/3 = 成功

$env:PYTHONPATH='C:\Users\张九思\206Dash\.pio-pylibs'
$env:PLATFORMIO_CORE_DIR='C:\206dash-scratch\pio-core-mix'
$env:PATH='C:\206dash-scratch\zigbin;' + $env:PATH
$env:PYTHONUTF8='1'          # ★ 不能省 —— 不设它，构建会以两种面目失败（2026-10-10 实测，各烧掉一次构建）：
                             #   ① [checkprogsize] UnicodeDecodeError: 'gbk' codec can't decode byte 0x85 ...
                             #      镜像其实**已经生成好**，只是末尾的尺寸检查用 GBK 去解码产物里的 UTF-8 中文
                             #   ② TypeError: argument should be a str or an os.PathLike object where
                             #      __fspath__ returns a str, not 'NoneType' —— 同一个病在配置阶段发作：7 秒就失败
                             #   ⇒ 判据看 [SUCCESS] 那一行，别只看退出码（成功时 pio 也可能返回 1）

# ★ 一律走 pio.ps1。本机裸 python 是"应用执行别名"占位：`python --version` 退出码 9009、零输出
.\tools\build\pio.ps1 -Cmd 'test -e native'                                              # 宿主机单元测试，不烧板
.\tools\build\pio.ps1 -Cmd 'run -e pcpreview -t exec'                                    # 本机渲双屏 BMP，Ctrl+C 后打开 preview/preview.html
.\tools\build\pio.ps1 -Cmd 'run -e esp32s3-rgb-master-now -t upload --upload-port COM9'   # 主板
.\tools\build\pio.ps1 -Cmd 'run -e esp32s3-rgb-slave-now  -t upload --upload-port COM8'   # 从板
```

★ **判据看 `[SUCCESS]` 那一行，别看退出码** —— 这台机器上 pio 编成功时也可能返回 1（与"裸 `python` 占位返回 0 却零产出"是同一个病的两面）。要判定产物是不是新生成的，再对一眼 mtime/哈希（帧看 `preview/frames/l_0030.bmp`，镜像看 `[SUCCESS]`）。

★ 两块板的分区表**不一样**，这是刻意的：有线档用 `partitions-s3.csv`（1MB app 槽 ×2 + OTA 槽），**无线档用 `partitions-s3-now.csv`**（单个 2MB `factory` 槽，**没有 OTA 槽**）—— 因为 ESP-NOW 把整个 WiFi 协议栈链进来，镜像 **1.49MB**，塞不进 1MB 槽。两张表的 `theme`/`spiffs`/`image`/`coredump` 偏移**刻意相同**，`nvs` 也都在 `0x9000`（所以**刷固件不会丢静音设置**）。

`theme`（16KB @ `0x210000`）与 `image`（经典板 1MB、S3 8MB @ `0x254000`）两个分区是运行时可换的：换配色或换图不用重编固件，esptool 命令由 `tools/theme-editor/` 的页面按目标板打印。素材还可以**导成一个 `assets.bin` 合并包**（页面里导出/导入同一份文件），格式见 `tools/theme-editor/ASSET-PACKAGE.md`。

刷机与测试的硬约束，都是踩过的：

- ★★ **烧写不要 patch 镜像自带头**：`esptool write_flash` 带显式 `--flash_mode qio --flash_freq 80m --flash_size 16MB`（**这三个值和 board JSON 一致**）会把从板打进 `TG0WDT_SYS_RST` 复位循环、app 日志零字节；同一批文件改用 `--flash_mode keep --flash_freq keep --flash_size keep` 立刻正常。**一律用 `keep`。**
- ★ 两块板**各自插自己的 `USB`（原生）Type-C 口**就能烧写与看日志（这两晚一直这么干，COM9=主板 / COM8=从板）。插哪个 Type-C 会改变 43/44 的归属（见 `ARCHITECTURE.md` §8.2），那也是"有线链路停用"的背景之一。
- ★ **别对同一个项目目录同时跑两个 PlatformIO**：实测会出现"上传 1 秒返回、什么都没烧"的假成功；判断依据是板子的 uptime 有没有归零。
- 开原生 USB 口的监视器必须 `monitor_rts = 0` / `monitor_dtr = 0`（`platformio.ini` 已写死），否则芯片可能被按在复位态 —— **开串口本身就可能把芯片踢进下载模式**，读完要确认板子还在跑。
- 分区表 CSV 必须**纯 ASCII**（PlatformIO 用系统编码读它），一个"★"就能让链接成功的构建在最后一步抛 `UnicodeDecodeError`。
- esptool v5 的进度条是 Unicode，控制台是 GBK 时会 `UnicodeEncodeError` 中断烧写 ⇒ 先 `$env:PYTHONIOENCODING='utf-8'`。
- `.pio-pylibs` 里那份 pyserial 不在系统 python 里，直接敲 `python tools/serial-capture/capture.py` 会 `ModuleNotFoundError: No module named 'serial'`。
- 表情画布不要超过 320，再大会盖住内圈副弧。
- native 测试：① 默认只转发"用例结果行"，测试里的 `printf` 要加 `-v`；② `-v` 会把未解析的行 echo 到 GBK 控制台，**测试里的中文 `printf` 会抛 `UnicodeEncodeError`** ⇒ 测试输出一律纯 ASCII，并且要显式 `fflush(stdout)`；③ 直接跑 `.pio\build\native\program.exe` 时 **CWD 必须是项目根**（4 条 `test_real_capture_*` 按相对路径读 CSV，否则假红 4 条）。

串口命令（`lib/dashcore/serial_cmd.h` 是唯一口径）：`d` 诊断页 · `r` 面板重新初始化 · `i` 数据注入 · `w` RF 测速/测丢包（只在无线档构建里有效）· `o` 抑制射频 · `t` 建连超时 · `u` OTA · `R` 重建。★ 原 `b`（蜂鸣器试响）/ `m`（静音开关）**随蜂鸣器一起删除**（2026-10-15）。

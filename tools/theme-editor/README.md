# 206Dash 界面工具（本地网页，不用装任何东西）

双击下面的 HTML 用浏览器打开即可 —— 不需要联网、不需要 Python、不需要起服务。

| 页面 | 管什么 | 刷到哪个分区 |
|---|---|---|
| `index.html` | **配色与几何**：背景色、弧线颜色/角度/半径、表情大小、开机动画时长 | `theme` 分区（16 KB @ `0x210000`） |
| `image-editor.html` | **图片资源**：背景图 + 两屏各一套表情差分 | `image` 分区（1 MB @ `0x254000`） |

两个分区彼此独立：只想换配色就只刷 `theme`，只想换图就只刷 `image`。
**两种都不需要重新编译固件。**

# 一、主题编辑器 `index.html`

## 能做什么

| 功能 | 说明 |
|---|---|
| **配色** | 背景色、表情底色（常态/红区）、五官色、**三条弧的点亮色与轨道色**（每条弧单独调） |
| **几何** | 每条弧的起始角/结束角/半径/线宽、轨道透明度、表情大小 |
| **数字读数** | 大数字/单位/水温三处的颜色、字号（48/18）、中心 y、显示开关 |
| **两屏独立** | 左屏（转速+水温）与右屏（车速）分别配；可关掉某条弧或整个表情 |
| **实时预览** | 右上是两屏的 480×480 实时画面，改一个参数立刻跟着变 |
| **阶段预览** | 右上角下拉框切 10 档（转速 4 档 / 车速 3 档 / 水温 3 档），预览里弧的进度、**两屏各自的表情**和数字读数都跟着那一档走 |
| **开机动画** | 下面那块并排画布能播「淡入 → 双屏错峰扫表 → 表情显形」，时长可调 |
| **导出/导入** | 导出 `theme.json`；也能把手改过的 JSON 粘回来或导入文件 |

**三条弧的配色在这里**：左屏 = 转速弧（外）+ 水温弧（内），右屏 = 车速弧，
每条都有「点亮色 / 轨道色 / 轨道透明度」三个控件。
控件上方有一行说明指路 —— 因为**图片编辑器那页也能改这三个颜色**
（用户是在那页对着表情图调色的），两页共用同一份配色，改哪边都算数。

> 预览里的表情是**程序化占位形状** —— 它只能表达"眯眼/睁大眼/张嘴/红底"，
> 要看**导入的表情图**在各阶段长什么样，用「表情导入」页右下那块「表情阶段模拟」。
>
> 两屏的表情在预览里是**分开**的：左屏(转速表)只看转速、右屏(速度表)只看车速，
> 所以点"车速·中"时左屏的脸不会变。
>
> 预览里的字体也是近似替代（浏览器自带字形）：**位置和字号可信，字宽只是近似**。

## 改完怎么用到设备上

导出的 `theme.json` 是**运行时主题**：刷进设备的 `theme` 分区就生效，**固件不用重新编译**。

```
; 1) 编辑完点右上角「导出主题文件」，得到 theme.json
; 2) 用 esptool 写到 theme 分区（偏移与大小见项目根目录 partitions.csv）
python -m esptool --chip esp32 -p <串口> write_flash 0x210000 theme.json

; 3) 复位，串口会打印:
;    theme: 已加载 (1805 字节, bg=0x141414, face=200)
```

| 参数 | 值 | 来源 |
|---|---|---|
| 分区偏移 | `0x210000` | `partitions.csv` 的 `theme` 行 |
| 分区大小 | `0x4000`（16 KB） | 同上 |
| 设备端缓冲上限 | 4096 字节 | `lib/themetool/theme_store.h` 的 `THEME_MAX_BYTES` |

> ⚠️ 三者必须一致：改 `partitions.csv` 要同步改这里的偏移；
> 改 `THEME_MAX_BYTES` 要确认不超过分区大小（否则会读越界）。
> 编辑器导出时会检查文件大小并提示是否超过 4096 字节。

**看不到 `theme:` 那行** 说明加载失败 —— 别慌，固件会**自动回退到默认主题继续跑**，
串口会明确打印失败原因（没有分区 / 读失败 / 解析失败）。这条降级路径是刻意设计的：
新手最容易卡在"刷了主题反而黑屏"，所以主题永远不该让固件起不来。

> `partitions.csv` 必须是**纯 ASCII**：PlatformIO 用系统编码（中文 Windows = GBK）
> 读这个文件，中文注释会直接让构建报 `UnicodeDecodeError`；加 UTF-8 BOM 则会
> 报 `Field 'type' can't be left empty`。两种都踩过，别再往里写中文。

`image ok: 5 张,数据 372 字节,镜像 1088 字节`）：

```

```

注意 `program.exe` 自己不会退出（`for(;;) loop()`），

## 字段与固件端必须一致

编辑器导出的字段名**必须**和 `lib/themetool/theme_store.cpp` 的解析器对得上，
否则字段会被当成"不认识"而忽略（不会报错，但也不生效）。**改字段时两边一起改**，
并跑一次 `python -m platformio test -e native`（主题解析有单测覆盖）。

字段含义：

- `bg_color` / `face_bg_idle` / `face_bg_redline` / `face_ink` / `track_color` / `value_color`
  —— 都是颜色，**`0xRRGGBB` 与十进制两种写法都接受**：固件解析器两种都吃
  （`theme_store.cpp` 的 `uintVal` 带 `0x` 分支），编辑器导入/粘贴时也会先把
  `0x` 转成十进制再解析（`theme-json.js`），所以手改过的文件能读回来。
  编辑器自己导出的写十进制 —— 想手改颜色的话，照 `theme-default.json` 的风格写 `0x` 更直观。
- `kind` —— 弧跟随哪个数据：**0=车速、1=转速、2=水温**
- `track_opa` —— 轨道透明度 0~255
- `start_deg` / `end_deg` —— **0°=3 点钟方向、顺时针增大**（与 LVGL 的 `lv_arc` 一致，
  源码 `lv_arc.c` 里就是 `x = r·sin(angle+90)`、`y = r·sin(angle)`）。
  默认值刻意让两条弧**开口方向相反**（用户要求：同向看着怪）：

  | 弧 | 角度 | 开口 | 形状 | 涨幅方向 |
  |---|---|---|---|---|
  | 转速弧（外） | **135 → 405** | 正下方 | 拱在表盘上方，从左下绕到右下 | 从 7:30 顺时针涨 |
  | 水温弧（内） | **0 → 180** | 正上方 | 兜在表盘下方，从 3 点钟绕到 9 点钟 | **镜像**：从左端(9 点钟)往右涨 |

  > "外圈拱上面、内圈兜下面"，一眼分得清哪条是哪条。
  > 水温弧之所以是 0→180（而不是更短的弧）：LVGL 的弧只能从 start 顺时针画到 end，
  > 而"开口朝上"要求覆盖区落在下半圆，唯一干净的写法就是 [0°, 180°]。
  > 但这样默认只会从**右端**开始亮，而水温表该从**左端**起涨 ——
  > 所以给它 `reverse: 1`（见下一条），点亮区从左端往右长。
  >
  > 朝向与涨幅方向都被实测验证过（沿弧带径向/周向扫固件落帧）：
  > 6 点钟只有水温弧、10:30 只有转速弧；水温 89℃ 时左端(170°)是点亮色、
  > 右端(15°)只是轨道。而预览里曾经因为角度换算多减了 90°，整块表被逆时针转 90°
  > （起点跑到 4:30、开口跑到正右方）—— 用户一眼看出来问"表的方向是不是要向右转 90 度"。
  > 现在两个编辑器的换算都不加偏移，`test-gauge-geometry.js` 盯着这几件事。
- `reverse` —— **涨幅方向（镜像）**：`0`（默认）= 从 `start` 端起涨；
  `1` = 从 `end` 端起涨。水温弧是 `1`。
  对应固件里的 `arc_set_progress()`：它决定"固定的是哪一端"。
  > 用户的原话："位置对了，但是涨幅方向反了，得做一下镜像。"
- `radius` / `width` —— **`radius` 是弧的"外沿"半径**（LVGL 把弧画在对象盒子内、
  外沿贴着盒子边），`width` 往**里**长：实际占 `[radius-width, radius]`。
  例：radius 205 / width 24 → 弧带落在 182..205，不是 193..217。
  > 预览也必须按这个语义画（canvas 描边以路径为中线，所以要画在 `radius - width/2`），
  > 否则预览里的弧会比真车向外偏半个带宽 —— 而"表情压没压到弧"正是这一页要看的。
- `radius` / `width` / `face_size` / `face.*` —— 都按 **480×480 基准**书写，
  真屏若是 800×800 会自动等比放大（`theme_scale()`）
- `screens[i].arc_count` —— 实际画几条弧（≤ 实际数组长度）
- `boot_*` —— 开机动画各阶段时长（毫秒）；`boot_total_ms` 由固件按
  「表情显形 + 一拍收尾」算出，**不用写**，写了也会被重算
- **`readout`** —— 表盘上的数字读数（转速/速度大数字 + 单位 + 水温数字）：
  - `digit_color` / `unit_color` / `coolant_color` —— 三处文字颜色（`0xRRGGBB`）
  - `digit_font` / `unit_font` —— 字号：**0 = 48 号（大）、1 = 18 号（小）**
  - `digit_cy` / `unit_cy` / `coolant_cy` —— 各处文字的**中心 y**（480 基准）
  - `show_units` / `show_coolant` —— 0/1 开关
  - 竖直可用区间只有 **47..120**（上面是弧带 23..47、下面是 240×240 表情图），
    所以默认 `digit_cy=72`、`unit_cy=107`；水温数字在表盘底部（默认 384），
    只有**转速表（左屏）**上有 —— 哪一屏有水温弧就在哪一屏显示
  - 大数字跟哪一路**由弧决定**（该屏第一条非水温弧），不是按屏幕序号写死的：
    把水温弧挪到别的屏、或者加第三条弧，读数会自动跟着走
  - **格式是固件里写死的**（速度取整到 1 km/h、转速取整到 10 rpm、水温到 1 ℃），
    主题只管颜色/字号/位置/开关 —— 改格式等于改代码，不放进主题

> 预览里的字体是近似的（浏览器自带字形），**位置和字号可信，字宽只是近似**。
> 要卡像素请用下面那套"落帧 + 读像素"的办法。

# 二、图片编辑器 `image-editor.html`

双击打开，**拖图片进去 → 选用途 → 导出 `image.bin` → 刷到 image 分区**。

## 仪表配色：这一页就能改，也能导出 theme.json

「尺寸与配色」下面的「仪表配色」有三块（左屏 转速弧 / 左屏 水温弧 / 右屏 车速弧），
每块都能用**颜色选择器**调 **点亮色 / 轨道色 / 轨道透明度** —— 和「预览底色」一样直接，
改完点「**导出 theme.json**」刷进 `theme` 分区就生效（固件不用重编译）：

```
python -m esptool --chip esp32 -p COM3 write_flash 0x210000 theme.json
```

| 按钮 | 作用 |
|---|---|
| **导出 theme.json** | 把当前配色（底色 + 三条弧）导成主题文件 |
| **读入 theme.json** | 读一份主题文件（也可以直接把 json 拖进页面） |
| **用固件默认** | 回到编译期默认配色 |

**两页共用同一份配色**：主题编辑器和这一页都读写同一个本机存储，
所以"在这页改了色，打开主题编辑器还是旧的"这种事不会发生；
反过来也一样。顺带解决了"改了半天、刷新一下全没了"。

**记录里连"基线"一起存**（`{v:2, base, theme}`，`base` = 存那一刻的固件默认值）。
为什么必须这样：只存用户的整份主题，**固件默认值一改就被旧记录挡住** ——
实测撞到过：水温弧从 `145→330` 改成 `0→180`（上方开口）之后，用户刷新页面
发现"什么都没变"，还以为是固件没改。现在读回来做逐字段三方比对：

| 情况 | 取值 |
|---|---|
| 用户改过的字段 | 保留用户的值 |
| 用户没碰过的字段 | 跟着**当前**默认值走 |

所以以后调默认值（弧的开口、角度、颜色、读数位置…），你刷新一下就能看到，
而你亲手调过的地方不会被动。旧格式的记录（没有基线、无法判断哪些是你改的）
会被**备份到 `206dash.theme.v1` 并忽略**，页面底部会说明这件事 ——
否则它会永远挡住新默认值。

**这一页只写"底色 + 三条弧"**：主题文件里其余的字段（五官几何、开机时长、
数字读出颜色/位置）在这里保持原样 —— 你从主题编辑器读过完整文件，导出就还是完整的；
没读过时导出的是**只有弧和底色的精简文件**，固件对缺失字段一律用默认值
（这是主题格式的设计），所以直接刷也安全。要调那些字段请用主题编辑器。

> 这一条改过两次，值得记下来：
> 1. 最初本页把弧色**写死**成红/绿/蓝 —— 你在主题编辑器改了色，这一页还按旧色预览，
>    而这一页正是用来看"表情叠在弧上什么效果"的。
> 2. 后来改成**只读**（从 theme.json 读）+ 指路"去主题编辑器改" ——
>    用户当场指出："那你做的读入 theme.json 功能有啥意义，一般用户也不会写。"
>    确实：让用户为了调三个颜色而先学会导出另一个文件，等于没做。
> 现在：**颜色选择器就在这一页 + 本页导出 + 两页共享同一份状态。**

## 能放什么

| 用途 | 设备上会做什么 |
|---|---|
| **表盘背景**（两屏通用） | 铺在最底层，弧线和文字盖在上面 |
| **左屏(转速表) × 4** | 常态 / 巡航 / 运动 / 红区 —— **只看转速** |
| **右屏(速度表) × 4** | 常态 / 巡航 / 运动 / 惊喜 —— **只看车速** |

**两屏是各自独立的状态机**，一共 8 张：

| 屏 | 状态 | 什么时候出现 | 角色号 |
|---|---|---|---|
| 左（转速表） | 常态 | 转速 < 1800（怠速 900 在这里） | 3 |
| 左 | 巡航 | 转速 ≥ 1800（稳定巡航 2000 在这里） | 12 |
| 左 | 运动 | 转速 ≥ 3500 | 13 |
| 左 | 红区 | 转速 ≥ 5000（上限 6000 前 1000 转） | 4 |
| 右（速度表） | 常态 | 车速 < 30 | 6 |
| 右 | 巡航 | 车速 ≥ 30 | 17 |
| 右 | 运动 | 车速 ≥ 90 | 18 |
| 右 | 惊喜 | 急加速 > 15 km/h/s（瞬时 400ms） | 8 |

- **转速三档按实车地标定**（点火怠速 900 / 稳定巡航 2000 / 表盘上限 6000）。
- **左屏不受车速影响、右屏不受转速影响**。测试把车速从 0 扫到 210 断言左屏不变，
  把转速从怠速 900 扫到表盘上限 6000 断言右屏不变 —— 这条是用户试用时提出来的。
- **水温不参与表情**：它只驱动水温弧和水温数字（那条弧开口朝上，见上面字段说明）。两个原因 ——
  一套水温表情要再加 4 张图（1MB 的 image 分区放不下）；水温是慢变量，
  屏幕下方本来就有弧和数字，再让脸跟着变容易误读（看到"冷车脸"会以为车有问题，
  其实只是刚启动）。
- 曾经还有过「眨眼」和「冷车/过热」，都已删除，编号 11/16 与 14/15/19/20 保留不复用。

**不用凑齐 8 张。** 缺图有**降级链**（`lib/dashcore/face_stages.h` 的
`kFaceFallback`）：运动缺图退巡航、惊喜缺图退运动……每个状态都一定能退到常态，
一张都没有才回落到程序化占位表情。**左右屏各查各的**：只导入左屏的图时，
右屏仍然走占位表情，不会拿左屏的图顶上。

保留编号 **2 / 5 / 7 / 9 / 10 / 11 / 14 / 15 / 16 / 19 / 20** 一律不复用
（分别是当年的开机帧、左屏惊喜、右屏红区、开机图、眨眼图、冷车/过热图）。
复用会让别人已导出的 `image.bin` 里那几张图静默变成别的表情。**新角色从 21 开始。**

**开机画面不在这里，也不占图片资源。** 它是程序化的（`boot_anim.cpp`：
淡入 → 双屏错峰扫表 → 表情显形），`boot_stagger_ms` 本来就让两屏错开启动，
观感上已经是两个不同的开机过程。用位图做开机画面要多占 144 KB，
还要多一套"什么时候显示哪张"的时序逻辑 —— 不值。

## 表情阶段模拟（这一页最有用的东西）

页面右下有一块**「表情阶段模拟」**：10 格 = 转速 4 档 + 车速 3 档 + 水温 3 档，
**每格并排画两块表**（左：转速表 / 右：速度表），下面按屏写明"该用哪张图"：

- 绿色的字 = 用自己那张图
- 橙色的字 = **缺那张图，退到了某张**（例：`左：缺「左屏表情·运动」→ 退到「左屏表情·红区」`）
- 红色的字 = 这一屏一张表情图都没有 → 占位表情

**为什么一格里要放两块表**：两屏是独立状态机，这样一眼就能看出
"点车速档时左屏纹丝不动"—— 只画一块表是看不出来的。

点格子 = 用它当大预览的阶段；上面的「阶段」下拉框可以切 9 档，
「左屏表情」「右屏表情」两个下拉框默认"跟随阶段"，也可以**各自单独指定** ——

## ⚠️ 1 MB 能放什么，不能放什么

一套完整表情是 **两屏各 4 张 = 8 张** + 背景。

先看单张的账（一张表情 = 宽×高×3 字节，RGB565A8；一张背景 = 宽×高×2 字节）：

| 单张尺寸 | 一张表情 | 一张背景 | 8 张表情 + 背景 | 1 MB 分区 |
|---|---|---|---|---|
| 320×320 | 300 KB | 200 KB | 2600 KB | ✗ |
| 288×288 | 243 KB | 162 KB | 2106 KB | ✗ |
| **240×240** | **169 KB** | **113 KB** | 1465 KB | ✗ 超 440 KB |
| 208×208 | 130 KB | 87 KB | 1127 KB | ✗ 超 100 KB |
| **192×192** | **108 KB** | **72 KB** | **936 KB** | **✓ 全放下，余 88 KB** |
| 160×160 | 75 KB | 50 KB | 650 KB | ✓ 很宽裕 |
| 128×128 | 48 KB | 32 KB | 416 KB | ✓ 还能再加别的 |

**这是"每屏 4 个状态"的直接收益**：14 个状态那版无论怎么调尺寸都装不下一整套，
8 张则有一个"全放下的工作点"（192×192）。

**现实用法（按优先级往里塞）**：

1. 先放 **240×240 背景一张**（113 KB）+ **左右屏「常态」各一张**（338 KB）——
   共约 450 KB，界面已经有了完整的"背景 + 表情"，其余状态降级到常态。
2. 再补齐两屏的「巡航」和「运动」（左右各两张 = 676 KB）—— 日常开车能看到的
   变化就都有了。
3. 想要 8 张全用 **240×240**，或者想加更多状态，就换 S3（16 MB flash）后把
   `image` 分区放大（分区表在 `partitions.csv`，代码不用动）。

编辑器左下有**占用条**，超了会在你点导出前直接报错（不会生成一个会被截断的 bin）。
默认尺寸是 240×240 —— 想一次放全 8 张的话，把每张改成 192 即可。

### 表情图带透明（已实现，用 RGB565A8）

表情叠在弧线上面，如果是不透明方块会把弧线挡掉一块。所以：

| 角色 | 颜色格式 | 每像素 | 为什么 |
|---|---|---|---|
| 表盘背景 | `RGB565`（`0x12`） | 2 字节 | 铺在最底层，透不透明没意义 |
| **表情（两屏各 4 态）** | **`RGB565A8`（`0x14`）** | **3 字节** | 要叠在弧线上，必须能透出底下的东西 |

"哪些角色算表情"不再手写一串判断，而是问 `face-stages.js`（与固件同源）——
以后加状态不会漏掉某一处、导致新表情丢掉 alpha 通道（那会变成黑边）。

`RGB565A8` 的布局是 **上半部 RGB565 平面 + 下半部独立 A8 平面**
（已在 LVGL 源码 `lv_draw_buf.c` 确认：`size = stride*h + (stride/2)*h`）。
所以它**每像素 3 字节**，不是 2。

**编辑器会自动按角色选格式**：表情图不铺底色、保留 alpha；背景图照旧铺底色合成。
你只要把带透明的 PNG 拖进表情角色就行。

> ⚠️ 改这个格式时**别用 `strideBytes()*h` 算总大小** —— 那不含追加的 alpha 平面，
> 会把合法镜像拒收。用 `ImageView::packedBytes()`。
> 这个坑实际踩过：打包器写 30000 字节、校验按 20000 算，报"尺寸不合法"，
> 而 blob 本身完全正确。现在有 `test_rgb565a8_size_includes_alpha_plane` 钉着。

### 逐帧满屏开机动画？不要想

480×480 × 12 帧 × 2 屏 = **10.5 MB**，比整块 4 MB flash 还大。
这也是两个 OTA 槽必须等大（各 1 MB）的原因 —— 不能再压缩它们来腾空间了。

## 刷写

```
python -m esptool --chip esp32 --port COM3 --baud 921600 write_flash 0x254000 image.bin
```

| 参数 | 值 | 来源 |
|---|---|---|
| 分区偏移 | `0x254000` | `partitions.csv` 的 `image` 行 |
| 分区大小 | `0x100000`（1 MB） | 同上 |
| 宿主机上限 | `IMAGE_PARTITION_BYTES` | `lib/themetool/image_blob.h` |

刷 1 MB 比刷 128 KB 慢，所以波特率给到 921600（115200 要一分半）。

**没刷过图片也能正常跑**：分区是空的（全 `0xFF`）时，固件解析会失败并
打印 `image: 镜像无效或未刷入,不用图片资源`，然后继续用纯色背景。
这条降级路径和主题一样是刻意设计的。

## 生成的二进制格式

```
偏移 0     : 镜像头 1420 字节
             +0  magic   = 0x44363032 ('206D')
             +4  version = 1
             +6  count   = 图片张数 (≤32)
             +8  data_bytes
             +12 索引表: 每项 44 字节 × 32
偏移 1420  : 像素数据（按索引表的 offset/size 排布）
```

索引项 44 字节 —— **没有任何对齐空洞**，每个字段都紧跟前一个：

| 项内偏移 | 字段 | 类型 |
|---|---|---|
| 0 | `offset` | u32（相对数据区起点） |
| 4 | `size` | u32 |
| 8 | `w` | u16 |
| 10 | `h` | u16 |
| 12 | `cf` | u8（LVGL 颜色格式，`0x12` = RGB565） |
| 13 | `stride_pad` | u8 |
| 14 | `role` | u16 |
| 16 | `order` | u16 |
| 18 | `name[24]` | char（必须留 `'\0'`） |

44 = 4+4+2+2+1+1+2+2+24，正好是 4 的倍数，所以尾部也不用填充。

> **`offset` 是 u32，这一条很关键。** 它曾经是 u16，把整个镜像的像素数据
> 卡在 64 KB 以内 —— 一张 480×480 背景就要 450 KB，1 MB 的分区等于白给。
> 更麻烦的是不报错：偏移溢出后设备端拿到错误的像素位置，画面是花的，
> 但日志一切正常。
>
> 另外，**别手算结构体对齐**。这里踩过两次：一次漏算了两个 u32 之间的洞，
> 一次多算了尾部填充。现在 C 侧有一条 `offsetof`/`sizeof` 断言
> （`test_entry_field_offsets`），JS 侧有"头部字段"一节，两边把同一张表
> 各钉一遍，往返测试再逐字节对账。

像素是 **RGB565 小端**（低字节在前）。写反了画面会"红蓝互换 + 竖条纹"。

## 改格式时怎么保证两边不跑偏

这个格式由**两套代码**共同维护，改错一处编译期完全看不出来：

- 生成方：`image-blob-build.js`（网页和 Node 都用它）
- 读取方：`lib/themetool/image_blob.cpp`（ESP32 固件）

所以有一个自动核对，**提交前跑一次**：

```powershell
pwsh tools/theme-editor/test-image-roundtrip.ps1
```

它做三件事：

1. Node 侧打包器单测（164 项断言：字节序、stride、对齐空洞、名字截断、坏输入必须报错）
2. 用 JS 打一个测试镜像 `.pio/image-test/image.bin`（同时生成可读的 `.manifest` 对账清单）
3. 跑 `pio test -e native`，让**固件自己的解析器**读这个镜像，逐字段、逐字节对账

这个核对抓出过两个真 bug（写索引项时用了上一轮循环遗留的变量，导致每项名字都相同；
像素循环漏了 x 偏移，导致每行重复第一个像素）—— 都是编译通过、肉眼看不出来的那种。

## 表盘朝向也要对账（`test-gauge-geometry.js`）

```powershell
node tools/theme-editor/test-gauge-geometry.js   # 26 项断言
```

管两件事：

1. **两个编辑器的角度换算不加任何偏移**。LVGL 的 `lv_arc` 是 0°=3 点钟、顺时针，
   而 canvas 的 `arc()` 约定完全一样 —— 所以 `d` 直接换成弧度即可。
   曾经两个页面都写成 `(d - 90)`，于是预览里的表**整体被逆时针转了 90°**：
   起点从 7:30 跑到 4:30、缺口从正下方跑到正右方。固件一直是对的，
   但用户先看到的是预览，于是问"表的方向是否需要向右旋转 90 度"。
2. **默认主题的满量程弧缺口在正下方**、起点在左下（135°）、`end > start`（顺时针增长）、
   内圈半径小于外圈、两条弧开口方向相反 —— 都是**产品决定**，写错了不报错、只是"看着怪"。

固件那一侧的朝向由 `check-preview-frame.js` 的「表盘朝向」检查兜着：
它读**真实落帧**，沿弧带扫一圈断言"正下方是缺口、正上方有弧"。

## 表情阶段表也要对账（`test-face-stages.js`）

```powershell
node tools/theme-editor/test-face-stages.js     # 230 项断言
```

它**解析 `lib/dashcore/face_stages.h` 的源码文本**（9 条阶段用例、缺图降级链、
槽位→角色编号三张表），与本目录的 `face-stages.js` 逐字段比对，
再和 `image-blob-build.js` 的角色编号比对一遍。

为什么值得单独一条：表情导入页的"阶段模拟"会告诉用户
"转速·中 = 左屏巡航脸、右屏常态脸"—— 这是刷图之前**唯一**能看到的证据。
网页那份表和固件那份不一致，预览就是在骗人，而真车上的表现要等刷完图才知道。

## 页面本身也要检查语法（`syntax-check-pages.js`）

```powershell
node tools/theme-editor/syntax-check-pages.js
node tools/theme-editor/test-theme-json.js
```

两个编辑器是**双击打开的静态 HTML**：没有构建、没有 lint，
语法错误的表现是"页面一片空白"或"点了没反应"，而不是一条报错。
这个脚本把每个内联 `<script>` 的正文交给 `new Function` 编译（不执行），
并检查 `<script>` 开合是否配对、引用的本地 `.js` 是否存在。
最后那条是踩过坑才加的：曾在页面中间多出一个 `</script>`，
后面几百行 JS 全跑到标签外面 —— 表现是空白页，而"每段脚本都能编译"的检查
完全查不出来（它们确实都能编译）。

`test-theme-json.js` 管的是另一件事：主题文件里的 `0xRRGGBB` 颜色，以及
**默认主题三处副本的一致性**。前者固件读得懂、而 `JSON.parse` 读不懂 ——
这条曾经让"导入 theme-default.json"直接报一句和颜色毫无关系的语法错。
它同时用真实的 `theme-default.json` 做回归，并断言"直接 JSON.parse 确实会失败"，
免得测试自己变成空转。

三处副本是：`lib/themetool/ui_theme.h` 的 `theme_set_defaults()`（固件的事实来源）、
`theme-default.json`（给人当模板）、`image-editor.html` 的 `ARC_FALLBACK`
（图片编辑器没读主题时的兜底弧）。它们不一致**不会报错**，只会表现成
"预览颜色不对"或者"照参考文件刷进去两个表左右颠倒"—— 后者真实发生过。

  （淡入 + 扫表 + 表情显形），"显形"的透明度切换对图片表情也生效
  （已实测：前 5 帧表情透明、之后可见）。
- **眨眼/定时表情**：`Blink` 状态已删除（与车速/转速/水温无关，也讲不出
  什么工况会触发）。稳态表情**只由数据决定、与时间无关** —— 这一点有单测钉住。
  要做"眼皮动"这类动作得引入多帧序列，目前没这个需求。
- **1 MB 装不下 240×240 的全套 8 张表情**（见上面那节；改成 192×192 就能全放下）。
  换 S3 后放大 `image` 分区即可。

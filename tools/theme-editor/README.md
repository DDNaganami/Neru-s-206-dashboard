# 206Dash 界面工具（本地网页，不用装任何东西）

双击下面的 HTML 用浏览器打开即可 —— 不需要联网、不需要 Python、不需要起服务。

| 页面 | 管什么 | 刷到哪个分区 |
|---|---|---|
| `index.html` | **配色与几何**：背景色、弧线颜色/角度/半径、表情大小、开机动画时长 | `theme` 分区（16 KB @ `0x210000`） |
| `image-editor.html` | **图片资源**：背景图 + 两屏各一套表情差分（**配色也在这一页**：底色、四条弧、四处读数颜色） | `image` 分区（经典板 1 MB / S3 板 8 MB @ `0x254000`，页面里选「目标板」） |

两个分区彼此独立：只想换配色就只刷 `theme`，只想换图就只刷 `image`。
**两种都不需要重新编译固件。**

# 一、主题编辑器 `index.html`

## 能做什么

| 功能 | 说明 |
|---|---|
| **配色** | 背景色、表情底色（常态/红区）、五官色、**四条弧的点亮色与轨道色**（每条弧单独调） |
| **几何** | 每条弧的起始角/结束角/半径/线宽、轨道透明度、表情大小 |
| **数字读数** | 大数字/单位/副表（水温、进气温度）各处的颜色、**字号档位**（大/小，点数随屏的分辨率走：480 屏 48/18、240 屏 24/10）、中心 y、显示开关 |
| **两屏独立** | 左屏（转速+水温）与右屏（车速）分别配；可关掉某条弧或整个表情 |
| **实时预览** | 右上是两屏的 480×480 实时画面，改一个参数立刻跟着变 |
| **阶段预览** | 右上角下拉框切 14 档（转速 4 / 车速 4 / 水温 3 / 进气温度 3），预览里弧的进度、**两屏各自的表情**和数字读数都跟着那一档走 |
| **开机动画** | 下面那块并排画布能播「淡入 → 双屏错峰扫表 → 表情显形」，时长可调 |
| **导出/导入** | 导出 `theme.json`；也能把手改过的 JSON 粘回来或导入文件 |

**四条弧的配色在这里**：左屏 = 转速弧（外）+ 水温弧（内），右屏 = 车速弧（外）+ 进气温度弧（内），
每条都有「点亮色 / 轨道色 / 轨道透明度」三个控件。
控件上方有一行说明指路 —— 因为**图片编辑器那页也能改这三个颜色**
（用户是在那页对着表情图调色的），两页共用同一份配色，改哪边都算数。

> 预览里的表情是**程序化占位形状** —— 它只能表达"眯眼/睁大眼/张嘴/红底"，
> 要看**导入的表情图**在各阶段长什么样，用「表情导入」页右下那块「表情阶段模拟」。
>
> 两屏的表情在预览里是**分开**的：左屏(转速表)只看转速、右屏(速度表)只看车速，
> 所以点"车速·中"时左屏的脸不会变。
>
> 预览里的字体也是近似替代（浏览器自带字形）：**位置和字号可信，字宽只是近似**。

## 改完怎么用到设备上

导出的 `theme.json` 是**运行时主题**：刷进设备的 `theme` 分区就生效，**固件不用重新编译**。

```
; 1) 编辑完点右上角「导出主题文件」，得到 theme.json
; 2) 用 esptool 写到 theme 分区（偏移与大小见项目根目录 partitions.csv）
python -m esptool --chip esp32 -p <串口> write_flash 0x210000 theme.json

; 3) 复位，串口会打印:
;    theme: 已加载 (1805 字节, bg=0x141414, face=200)
```

| 参数 | 值 | 来源 |
|---|---|---|
| 分区偏移 | `0x210000` | `partitions.csv` 的 `theme` 行 |
| 分区大小 | `0x4000`（16 KB） | 同上 |
| 设备端缓冲上限 | 4096 字节 | `lib/themetool/theme_store.h` 的 `THEME_MAX_BYTES` |

> ⚠️ 三者必须一致：改 `partitions.csv` 要同步改这里的偏移；
> 改 `THEME_MAX_BYTES` 要确认不超过分区大小（否则会读越界）。
> 编辑器导出时会检查文件大小并提示是否超过 4096 字节。

**看不到 `theme:` 那行** 说明加载失败 —— 别慌，固件会**自动回退到默认主题继续跑**，
串口会明确打印失败原因（没有分区 / 读失败 / 解析失败）。这条降级路径是刻意设计的：
新手最容易卡在"刷了主题反而黑屏"，所以主题永远不该让固件起不来。

> `partitions.csv` 必须是**纯 ASCII**：PlatformIO 用系统编码（中文 Windows = GBK）
> 读这个文件，中文注释会直接让构建报 `UnicodeDecodeError`；加 UTF-8 BOM 则会
> 报 `Field 'type' can't be left empty`。两种都踩过，别再往里写中文。

## 不上设备也能看效果（宿主机预览）

图片资源也能这样验（**已实测**：输出 262 帧，串口打印
`image ok: 5 张,数据 372 字节,镜像 1088 字节`）：

```
$env:IMAGE_BLOB = "C:\...\.pio\image-test\image.bin"   ; 或编辑器导出的 image.bin

```

注意 `program.exe` 自己不会退出（`for(;;) loop()`），
跑够了就 Ctrl+C —— 帧写在 `preview/frames/`，与退出方式无关。

## 字段与固件端必须一致

编辑器导出的字段名**必须**和 `lib/themetool/theme_store.cpp` 的解析器对得上，
否则字段会被当成"不认识"而忽略（不会报错，但也不生效）。**改字段时两边一起改**，
并跑一次 `python -m platformio test -e native`（主题解析有单测覆盖）。

字段含义：

- `bg_color` / `face_bg_idle` / `face_bg_redline` / `face_ink` / `track_color` / `value_color`
  —— 都是颜色，**`0xRRGGBB` 与十进制两种写法都接受**：固件解析器两种都吃
  （`theme_store.cpp` 的 `uintVal` 带 `0x` 分支），编辑器导入/粘贴时也会先把
  `0x` 转成十进制再解析（`theme-json.js`），所以手改过的文件能读回来。
  编辑器自己导出的写十进制 —— 想手改颜色的话，照 `theme-default.json` 的风格写 `0x` 更直观。
- `kind` —— 弧跟随哪个数据：**0=车速、1=转速、2=水温、3=进气温度**（★ 只能往后加：这个数就是存进 theme.json 的值，插队会让老主题文件里的弧换意思）
- `track_opa` —— 轨道透明度 0~255
- `start_deg` / `end_deg` —— **0°=3 点钟方向、顺时针增大**（与 LVGL 的 `lv_arc` 一致，
  源码 `lv_arc.c` 里就是 `x = r·sin(angle+90)`、`y = r·sin(angle)`）。
  默认值刻意让**外圈弧与内圈副弧开口方向相反**（用户要求：同向看着怪）：

  | 弧 | 角度 | 开口 | 形状 | 涨幅方向 |
  |---|---|---|---|---|
  | 转速弧（左屏·外） | **135 → 405** | 正下方 | 拱在表盘上方，从左下绕到右下 | 从 7:30 顺时针涨 |
  | 车速弧（右屏·外） | **135 → 405** | 正下方 | 同上（右屏那条） | 从 7:30 顺时针涨 |
  | 水温弧（左屏·内） | **0 → 180** | 正上方 | 兜在表盘下方，从 3 点钟绕到 9 点钟 | **镜像**：从左端(9 点钟)往右涨 |
  | 进气温度弧（右屏·内） | **0 → 180** | 正上方 | 与水温弧**逐字段相同**，只换屏与颜色 | **镜像**（同上） |

  > "外圈拱上面、内圈兜下面"，一眼分得清哪条是哪条。
  > 两条**副弧**（水温 / 进气温度）的几何由 `test-gauge-geometry.js` 的
  > 「进气温度弧 = 水温弧的镜像版」逐项比对 —— 用户要的是"进气温度像水温表
  > 在转速表上那样待在速度表上"，所以这四行里只有屏号与颜色允许不同。
  > 副弧之所以是 0→180（而不是更短的弧）：LVGL 的弧只能从 start 顺时针画到 end，
  > 而"开口朝上"要求覆盖区落在下半圆，唯一干净的写法就是 [0°, 180°]。
  > 但这样默认只会从**右端**开始亮，而水温/进气温度表该从**左端**起涨 ——
  > 所以给它 `reverse: 1`（见下一条），点亮区从左端往右长。
  >
  > 朝向与涨幅方向都被实测验证过（沿弧带径向/周向扫固件落帧）：
  > 6 点钟只有副弧、10:30 只有外圈弧；水温 89℃ 时左端(170°)是点亮色、
  > 右端(15°)只是轨道；进气温度同理（左端 `#ffb220` 点亮、右端轨道）。
  > 而预览里曾经因为角度换算多减了 90°，整块表被逆时针转 90°
  > （起点跑到 4:30、开口跑到正右方）—— 用户一眼看出来问"表的方向是不是要向右转 90 度"。
  > 现在两个编辑器的换算都不加偏移，`test-gauge-geometry.js` 盯着这几件事。
- `reverse` —— **涨幅方向（镜像）**：`0`（默认）= 从 `start` 端起涨；
  `1` = 从 `end` 端起涨。两条副弧（水温、进气温度）都是 `1`。
  对应固件里的 `arc_set_progress()`：它决定"固定的是哪一端"。
  > 用户的原话："位置对了，但是涨幅方向反了，得做一下镜像。"
- `radius` / `width` —— **`radius` 是弧的"外沿"半径**（LVGL 把弧画在对象盒子内、
  外沿贴着盒子边），`width` 往**里**长：实际占 `[radius-width, radius]`。
  例：radius 205 / width 24 → 弧带落在 181..205，不是 193..217。
  > 预览也必须按这个语义画（canvas 描边以路径为中线，所以要画在 `radius - width/2`），
  > 否则预览里的弧会比真车向外偏半个带宽 —— 而"表情压没压到弧"正是这一页要看的。
- `radius` / `width` / `face_size` / `face.*` —— 都按 **480×480 基准**书写，
  真屏若是 800×800 会自动等比放大（`theme_scale()`）
- `screens[i].arc_count` —— 实际画几条弧（≤ 实际数组长度）
- `boot_*` —— 开机动画各阶段时长（毫秒）；`boot_total_ms` 由固件按
  「表情显形 + 一拍收尾」算出，**不用写**，写了也会被重算
- **`readout`** —— 表盘上的数字读数（转速/速度大数字 + 单位 + 水温数字）：
  - `digit_color` / `unit_color` / `coolant_color` / `intake_color` —— 四处文字颜色（`0xRRGGBB`）
    （水温绿 `0x7CFF6B`、进气琥珀 `0xFFB020`，与各自那条弧同色，一眼能对上）
    ★ **老主题文件里没有这一段**（这几个字段是后加的）：缺哪个就用固件默认值
    （`theme_store.cpp` 对不认识的键跳过、对缺失的键**不动**，所以是"用默认值"而不是"变黑"）——
    于是老文件刷进去，画面与今天**完全一样**，不必为新字段改动任何已有主题。
    ★ 这四处颜色**两个编辑器里都能改**：图片编辑器「尺寸与配色」下面也有四个色块
    （见下面「仪表配色」那一节）—— 换底图的那一页就能直接把字改成看得见的颜色。
  - `digit_font` / `unit_font` —— 字号**档位**：**0 = 大数字档、1 = 单位/副表档**。
    ★ 点数不是固定的，**跟着屏的分辨率查表**（`lib/themetool/ui_theme.h` 末尾的
    `kReadoutFontPx`）：480 屏上 48 / 18 号，**240 屏上 24 / 10 号**。
    所以同一份 `theme.json` 在两种屏上都成立 —— 换屏不用重做主题，
    而主题里存的永远是档位、不是点数（存点数换屏就废了）。
  - `digit_cy` / `unit_cy` / `coolant_cy` / `intake_cy` —— 各处文字的**中心 y**（480 基准）
  - `show_units` / `show_coolant` / `show_intake` —— 0/1 开关
  - 竖直可用区间只有 **59..120**（上面是**外弧带 35..59**：`radius` 205 是**外沿**、
    `width` 24 往内长，所以是 205-24=181 → 240-181=59，不是旧文档里的 23..47；
    下面是表情图顶边 120），
    所以默认 `digit_cy=72`、`unit_cy=107`；**两条副表的数字都在各自屏底部**
    （默认 384，`coolant_cy` 与 `intake_cy` 是两个独立字段，
    万一有人把两条副弧放到同一屏也能各自挪开）：
    水温在**左屏（转速表）**、进气温度在**右屏（速度表）** ——
    哪一屏有那条副弧就在哪一屏显示
    （实测 48 号数字墨迹顶在 y=55，蹭进弧带内沿 4 像素，是刻意接受的：
    读数建在弧**之后**，压在弧上面；往下挪 4 像素去躲，单位就会贴到表情顶边）
  - 大数字跟哪一路**由弧决定**（该屏第一条**非副表**弧；副表 = 水温或进气温度），不是按屏幕序号写死的：
    把水温弧挪到别的屏、或者加第三条弧，读数会自动跟着走（固件里的判定是 `is_aux_kind()`）
  - **格式是固件里写死的**（速度取整到 1 km/h、转速取整到 10 rpm、温度到 1 ℃），
    主题只管颜色/字号/位置/开关 —— 改格式等于改代码，不放进主题

> 预览里的字体是近似的（浏览器自带字形），**位置和字号可信，字宽只是近似**。
> 要卡像素请用下面那套"落帧 + 读像素"的办法。

## 微雪双屏 240×240（验证用的那块板，2026-09-22 已退货）—— 图片从零到屏上

板子是 **ESP32-S3-DualEye-Touch-LCD-1.28**（两块 240×240 圆屏 GC9A01A），
固件是 `[env:esp32s3-spi]`（`-DTHEME_DISPLAY_RES=240`，分区表 `partitions-s3.csv`）。
下面的尺寸、字节数、刷写命令都在这台机器上实测过（整套素材还过了**固件自己的解析器**
的逐字节对账）；最后"屏上对不对"按第 5 节的眼睛验收。**换图只刷 image 分区，不动固件**。

> **★ 2026-09-22（owner 确认）**：这块 **DualEye 板已退货**（240 档验证已完成并被接受），
> 所以**本节保留供同类板参考** —— 下面的尺寸 / 字节数 / 命令都是当年在这台机器上实测的数，
> **结论与 240 档都仍然有效**（`spec-240.json`、`ui_theme.h` 的 240 字号档、`[env:esp32s3-spi]` 都还在），
> 只是**现在手上没有这块硬件**（手上的显示硬件只有无屏的裸 S3 抓帧盒，见仓库根 `README.md`）。
> **步骤一条没删**：换同类 240 板时照做即可，端口 / 识别到的设备名要按新板重新看。

### 1. 选目标板：`ESP32-S3 微雪双屏 240×240（1.28"）`（`s3_240`）

图片编辑器右侧「占用 → 目标板」下拉框。**默认停在第 0 项「经典 ESP32」**，
所以每打开一次页面先看这一眼——它决定"画布上限 / 占用分母 / 刷写命令的 `--chip`"：

| | **s3_240**（这块板） | 经典板 / S3（480 屏） |
|---|---|---|
| image 分区 | **8 MB** @ `0x254000` | 1 MB / 8 MB |
| 表情画布**上限** | **160** | 320 |
| 表情**推荐** | **152** | 300 |
| 满屏背景 | **240×240** | 480×480 |
| 刷写 `--chip` | `esp32s3` | `esp32` / `esp32s3` |

为什么是 160/152：图是**原尺寸居中**画的（`dash_ui.cpp` 里只有 `lv_image_create` +
`lv_obj_center`，**没有** `lv_image_set_scale`），而屏心两圈弧压在它**下面**。
240 屏上整套几何是 480 的 0.5 倍，内圈副弧内沿只剩半径 **81** ⇒ 画布上限 160、推荐 152。
一张 300×300 的图在 240 屏上比整块屏还大：**盖住副弧，而且不报错**。
背景同理要 240×240——480 的底图只会露出中间那块（图的中心 240×240 区域）。

### 2. 十张表情 + 一张背景：角色号 → 哪块屏、哪一档

来源：`lib/dashcore/face_stages.h` 的 `kFaceRoleId`（槽位→编号）与
`lib/themetool/image_blob.h` 的 `ImageRole`（编号本身）。**左屏 = 转速表，右屏 = 速度表**
（法系车，别按"左车速右转速"理解）。背景两屏**共用一张**。

| 角色号 | 屏 | 档位 | 什么时候出现 | 建议文件名 |
|---|---|---|---|---|
| **1** | 两屏共用 | 表盘背景 | 一直在最底层（弧线压在它上面） | `bg.png` |
| **3** | 左（转速表） | 怠速/常态 | 转速 < 1500（怠速 900 就在这档） | `L_idle.png` |
| **12** | 左 | 巡航 | 转速 1500（1580 进 / 1420 退） | `L_cruise.png` |
| **13** | 左 | 运动 | 转速 3500（3580 / 3420） | `L_sport.png` |
| **21** | 左 | 高转 | 转速 4500（4580 / 4420） | `L_high.png` |
| **4** | 左 | 红区 | 转速 5800（5880 / 5720，断油 6300） | `L_redline.png` |
| **6** | 右（速度表） | 静止 | 车速 < 30 | `R_idle.png` |
| **22** | 右 | 市区 | 车速 30（33 / 27） | `R_city.png` |
| **17** | 右 | 快速路 | 车速 65（68 / 62） | `R_cruise.png` |
| **18** | 右 | 高速 | 车速 95（98 / 92） | `R_sport.png` |
| **8** | 右 | 超速 | 车速 > 130（退 127，迟滞） | `R_overspeed.png` |

**不用凑齐 11 张**：缺哪一档就走降级链（`kFaceFallback`，例：高转→运动→红区→巡航→怠速），
一张都没有才回落到程序化占位表情。**两屏各查各的**：只导了左屏的图，右屏仍是占位表情。
保留编号 2 / 5 / 7 / 9 / 10 / 11 / 14 / 15 / 16 / 19 / 20 **一律不复用**（新角色从 21 起）。

### 3. 做图 → 导出 `image.bin`

1. 双击打开 `image-editor.html`，目标板选「**微雪双屏 240×240**」；
2. 拖 PNG 进去（背景 1 张 240×240、表情最多 10 张 152×152，带透明的 PNG 更好——
   页面按角色自动选格式：背景 `RGB565` 2 字节/像素、表情 `RGB565A8` 3 字节/像素）；
3. 每张的「用途」下拉框选上面表里的角色（新图默认依次给：背景 → 左屏常态 → 右屏常态）；
   尺寸那栏填 240 / 152（预设按钮里有），**别让它超过 160**；
4. 右下「表情阶段模拟」点格子看效果——预览画布已经按**目标板的屏**合成，
   240 档就是 240×240（1 像素 = 屏上 1 像素），看到什么屏上就是什么；
5. 「导出 image.bin」。占用条会按 8 MB 分区算：**一整套（1 背景 + 10 张 152）≈ 791 KB，只占 9.7%**。

命令行等价物（自动化 / 复现，同一个打包器、同一套字节；`spec-240.json` 是占位图案，
只用来验证尺寸和命令，正式素材请走上面那 5 步）：

```powershell
node tools/theme-editor/build-image-bin.js --spec tools/theme-editor/spec-240.json `
     --out image.bin --target s3_240
# 实测：809740 字节 = 头 1420 + 背景 240×240×2 + 10×152×152×3，11 张，占 8MB 的 9.7%
```

> **想刷之前先让固件自己的解析器核对一遍**（不用上板）：打包时会同时写出
> `image.bin.manifest`（逐行十六进制对账清单），把它和镜像一起喂给 native 测试：
>
> ```powershell
> # 在纯 ASCII 副本里跑（中文路径会让 xtensa/zig 失败，见仓库根 README）
> $env:IMAGE_BLOB='<绝对路径>\image.bin'
> $env:IMAGE_BLOB_MANIFEST='<绝对路径>\image.bin.manifest'
> python -m platformio test -e native     # 看 test_js_blob_roundtrip [PASSED]
> ```
>
> 实测：一整套 240 素材（809740 字节 / 11 张，含 240 行的背景与 RGB565A8 的
> A8 平面）**逐字节通过**。★ 宿主机那道闸门是 1 MB（`IMAGE_BLOB_MAX_BYTES`
> 的经典板口径）：240 这块板用满 160 的整套是 884620 字节，够；
> 但 S3 上 480 档那种 3 MB 的整套核不了 —— 那是宿主机上限的事，不是镜像不对。

### 4. 只刷 image 分区（**不用重编固件、不用重烧 app**）

`theme` 与 `image` 是两个独立分区。刷 image **只改图片**，固件一个字节都不动，
所以改图迭代的循环是"导出 → 刷 → 重启"，没有编译。

```powershell
# ★ 2026-09-22：这块 DualEye 板已退货，本行保留供同类板参考（COM5 是当时那台机器上的口）。
# ★ 端口改成你板子的那个：这块 DualEye 走**原生 USB**，本机是 COM5（不是 COM3）。
# ★ 三个路径缺一不可，否则会报 No module named 'esptool' / 'intelhex'：
#     esptool 本体（PlatformIO 装的）/ stubs（intelhex 等替身包）/ pyserial 所在的 .pio-pylibs
$env:PYTHONPATH='C:\Users\Public\206dash\.pio-core\packages\tool-esptoolpy;C:\Users\Public\206dash\stubs;C:\Users\张九思\206Dash\.pio-pylibs'
python -m esptool --chip esp32s3 --port COM5 --baud 921600 write_flash 0x254000 image.bin
```

| 参数 | 值 | 来源 |
|---|---|---|
| `--chip` | `esp32s3`（**不是 `esp32`**，写错 esptool 当场拒绝） | 目标板 = s3_240 |
| 分区偏移 | `0x254000` | `partitions-s3.csv` 的 `image` 行（两份分区表刻意相同） |
| 分区大小 | `0x800000`（8 MB） | 同上 |
| 成功标志 | 最后一行 **`Hash of data verified.`** | esptool 4.11 |

> 这一条踩过两次（照抄旧文就失败）：① 文档里只写了 `python -m esptool`（本机系统 python
> 里没装它，必须带 `PYTHONPATH`）；② `--port COM3` 是占位值，这块板是 **COM5**。
> 页面「3 · 刷写」那栏印的就是这条命令（`--chip` 按目标板给），端口和 `PYTHONPATH` 要自己补。
> ★ 偏移以分区表那一行为准（`0x254000`）：写错地方 esptool **照样打 `Hash of data verified.`**
> —— 症状是"屏上什么都没变"，而且写偏了还会顺手把 `theme` 区（`0x210000`，只有 16KB）压掉。

### 5. 刷完重启，按这个顺序验收

1. 复位（或断电重上）。开机先看**程序化扫表动画**（两屏错峰）——它在，说明固件跑起来了；
2. 扫完：**底图铺满整屏**（弧带外沿在半径 ~102）、两圈弧压在底图**上面**、表情居中在最上层、
   数字读数在最上面；左屏转速表（+水温弧）、右屏速度表（+进气温度弧）；
3. 串口那几行对账（115200，两个 USB 口都有日志）：
   `image : 分区 8192 KB @ 0x254000(编译期口径 8192 KB)`、
   `image ok: 11 张,数据 808320 字节,镜像 8388608 字节`
   （张数/字节数跟着你导的那套走，上面是 `spec-240.json` 那一套的数；
   最后那个"镜像"是**分区大小**，不是文件大小——mmap 的是整个分区）、
   一张图都没加载时是 `image none: 无图片资源,背景用主题纯色`；
4. **最快确认"换图生效"的办法：换背景**。把背景换成一张纯色图刷进去重启，底色立刻变——
   表情要踩到对应档位才出现（怠速 900 转就是「常态」那张），背景是每帧都在的。

### 6. 没上屏 / 不对，按这个顺序排查

| 现象 | 最可能的原因 | 怎么确认 |
|---|---|---|
| 屏上完全没变化，串口 `image none:` | 没刷进这个分区 / 偏移写错 | esptool 是否打了 `Hash of data verified.`；偏移是否 `0x254000` |
| 串口 `image: 镜像无效或未刷入` | 分区里不是合法镜像（刷了别的文件、只写了一半） | 重新刷一次 `image.bin`；文件大小对不对 |
| 图**被裁**、表情盖住副弧、背景只剩中间一块 | **目标板选错成 480 档**（按 300/480 做的图） | 页面上限应是 160/推荐 152/背景 240；重导一次 |
| 脸的**档位对不上**（该变不变） | 角色选错（编号 → 屏/档位见表 2） | 页面阶段模拟里那行"用「左屏表情·X」"就是固件会用的角色 |
| 某档一直是**别的脸** | 那一档没导入，走了降级链 | 页面上那行是橙色的（"缺「…」→ 退到「…」"），这是设计行为 |
| 右屏一直是占位表情 | 只导入了左屏的角色 | 表 2 里右屏那 5 个角色要各自导一张 |
| 改了图但屏上还是旧的 | 刷完没重启（镜像只在 `setup()` 里 mmap 一次） | 复位一次 |


## 仪表配色：这一页就能改，也能导出 theme.json

「尺寸与配色」下面的「仪表配色」有四块（左屏 转速弧 / 左屏 水温弧 / 右屏 车速弧 / 右屏 进气温度弧），
每块都能用**颜色选择器**调 **点亮色 / 轨道色 / 轨道透明度** —— 和「预览底色」一样直接，
改完点「**导出 theme.json**」刷进 `theme` 分区就生效（固件不用重编译）：

```
python -m esptool --chip esp32 -p COM3 write_flash 0x210000 theme.json
```

> ★ 在**微雪双屏 240** 那块板上这条要改成 `--chip esp32s3 -p COM5`，并且先挂上
> 三路径 `PYTHONPATH`——和刷 image 分区是同一条命令，只换偏移（完整写法与踩过的坑
> 见上面「微雪双屏 240×240」第 4 步）。

### 读数颜色（屏上的字）

弧那一块下面还有一块「**读数颜色（屏上的字）**」，同样是色块 + 色号，四处：

| 控件 | 管的是 | 默认 |
|---|---|---|
| 大数字 | 两屏正上方那个大数字（转速 / 车速） | `#FFFFFF` 白 |
| 单位 km/h · rpm | 大数字下面那一行 | `#9AA0A6` 灰 |
| 水温（左屏） | 左屏底部的 `88°C` | `#7CFF6B` 绿（与水温弧同色） |
| 进气温度（右屏） | 右屏底部的 `35°C` | `#FFB020` 琥珀（与进气弧同色） |

为什么要在这里就能改，而不是"去主题编辑器改"：**底图是用户自己换的**。
换一张浅色底图之后，默认的浅色字（数字白、单位灰）在屏上**整片看不见**，
而且不会有任何报错 —— 而"对着底图看效果"正是这一页。改完**右边的预览立刻跟着变**
（预览里现在会画出读数，与固件同一套位置/字号/开关），所以**预览就是这里的把关人**：
颜色和底图够不够分得开，看一眼就知道，不需要另外的检查器。

> 字号 / 中心 y / 显示开关（`digit_font` / `*_cy` / `show_*`）仍归**主题编辑器** ——
> 那几个字段要对着几何调，这一页不提供控件、**也不会把它们写进导出的文件**
> （缺失 = 固件默认值，与这一页的其它字段同一套规矩）。

| 现象 | 最可能的原因 | 怎么办 |
|---|---|---|
| **屏上的字看不见 / 糊在底图里** | 读数颜色还是默认的浅色（数字白、单位灰），而底图是浅色的 | 在这一页「读数颜色」把**大数字 / 单位**改成深色（浅底 → 深字），**看右边的预览**确认，再导出 `theme.json` 刷 `theme` 分区 |

| 按钮 | 作用 |
|---|---|
| **导出 theme.json** | 把当前配色（底色 + 四条弧 + 四处读数颜色）导成主题文件 |
| **读入 theme.json** | 读一份主题文件（也可以直接把 json 拖进页面） |
| **用固件默认** | 回到编译期默认配色 |

**两页共用同一份配色**：主题编辑器和这一页都读写同一个本机存储，
所以"在这页改了色，打开主题编辑器还是旧的"这种事不会发生；
反过来也一样。顺带解决了"改了半天、刷新一下全没了"。

**记录里连"基线"一起存**（`{v:2, base, theme}`，`base` = 存那一刻的固件默认值）。
为什么必须这样：只存用户的整份主题，**固件默认值一改就被旧记录挡住** ——
实测撞到过：水温弧从 `145→330` 改成 `0→180`（上方开口）之后，用户刷新页面
发现"什么都没变"，还以为是固件没改。现在读回来做逐字段三方比对：

| 情况 | 取值 |
|---|---|
| 用户改过的字段 | 保留用户的值 |
| 用户没碰过的字段 | 跟着**当前**默认值走 |

所以以后调默认值（弧的开口、角度、颜色、读数位置…），你刷新一下就能看到，
而你亲手调过的地方不会被动。旧格式的记录（没有基线、无法判断哪些是你改的）
会被**备份到 `206dash.theme.v1` 并忽略**，页面底部会说明这件事 ——
否则它会永远挡住新默认值。

**这一页只写"底色 + 四条弧 + 读数颜色"**：主题文件里其余的字段（五官几何、开机时长、
读数的**字号/位置/显示开关**）在这里保持原样 —— 你从主题编辑器读过完整文件，导出就还是完整的；
没读过时导出的是**只有底色、弧和这四个颜色的精简文件**，固件对缺失字段一律用默认值
（这是主题格式的设计），所以直接刷也安全。要调那些字段请用主题编辑器。

> 读数颜色（`digit_color` / `unit_color` / `coolant_color` / `intake_color`）是其中唯一
> 被本页**写进文件**的非弧字段 —— 因为它正是"换底图之后看不见字"的解药，
> 而这一页就是换底图的地方。反过来，这一页**不写**读数的位置与开关：
> 那几个数这一页没有控件，抄进文件只会变成"看不出来源的数"，还会挡住以后改默认值。
> 老主题（没有 `readout`、或里面只有位置）在这一页会补上**固件默认色**预览、导出，
> 所以画面与今天一致（`test-theme-json.js` 对着 `ui_theme.h` 钉着这条）。

> 这一条改过两次，值得记下来：
> 1. 最初本页把弧色**写死**成红/绿/蓝 —— 你在主题编辑器改了色，这一页还按旧色预览，
>    而这一页正是用来看"表情叠在弧上什么效果"的。
> 2. 后来改成**只读**（从 theme.json 读）+ 指路"去主题编辑器改" ——
>    用户当场指出："那你做的读入 theme.json 功能有啥意义，一般用户也不会写。"
>    确实：让用户为了调三个颜色而先学会导出另一个文件，等于没做。
> 现在：**颜色选择器就在这一页 + 本页导出 + 两页共享同一份状态。**

## 能放什么

| 用途 | 设备上会做什么 |
|---|---|
| **表盘背景**（两屏通用） | 铺在最底层，弧线和文字盖在上面 |
| **左屏(转速表) × 5** | 怠速 / 巡航 / 运动 / **高转** / 红区 —— **只看转速** |
| **右屏(速度表) × 5** | 静止 / **市区** / 快速路 / 高速 / 超速 —— **只看车速** |

**两屏是各自独立的状态机**，一共 10 张：

| 屏 | 状态 | 什么时候出现（括号里是进 / 退两个门槛） | 角色号 |
|---|---|---|---|
| 左（转速表） | 怠速 | 转速 < 1500（怠速 900、冷车快怠速 1250 都在这里） | 3 |
| 左 | 巡航 | 转速 1500（1580 进 / 1420 退）—— 日常全段 | 12 |
| 左 | 运动 | 转速 3500（3580 进 / 3420 退）—— 扭矩峰 4000 在这段 | 13 |
| 左 | **高转** | 转速 4500（4580 进 / 4420 退）—— 功率带（最大功率 5750） | **21** |
| 左 | 红区 | 转速 5800（5880 进 / 5720 退）—— **断油 6300**，留 420 转提前量 | 4 |
| 右（速度表） | 静止 | 车速 < 30（含泊车/堵车蠕行） | 6 |
| 右 | **市区** | 车速 30（33 进 / 27 退）—— 市区限速 30~60 | **22** |
| 右 | 快速路 | 车速 65（68 进 / 62 退）—— 环路限速 70~90 | 17 |
| 右 | 高速 | 车速 95（98 进 / 92 退）—— 限速 100~120 | 18 |
| 右 | 超速 | 车速 **> 130**（回落到 127 以下才退出，有迟滞） | 8 |

> ★ **为什么是每屏 5 档**（2026-09-18 定，依据是 TU5JP4 + AL4 的实际活动范围，
> 那笔账在 `lib/dashcore/expression.cpp` 顶部）：
> · 左屏加「高转」：4000（扭矩峰）和 5750（功率峰）是两种体感，
>   而且 1 档 50km/h、2 档 80km/h 全油门真能走到 4500 以上；
> · 右屏加「市区」：原来 30~90 合成一档，等于把"市区跟车"和"环路 90"
>   画成同一张脸，而这两件事的档位、转速、注意力都不一样；
> · **分界刻意避开日常落脚点**（1600~3400 转之间一个分界都不放）——
>   4 档巡航 100~130km/h 是 2600~3400 转，贴着边界的话脸会一直抖。
>
> ★ **新增角色号从 21 起接**（21=左屏·高转，22=右屏·市区），
> 2/5/7/9/10/11/14/15/16/19/20 是保留号，一律不复用（复用会让别人已导出的
> `image.bin` 里那几张图静默变成别的表情）。

> **超速这一档原来叫「惊喜」**（急加速 > 15 km/h/s 的 400ms 瞬态），已改成**超速**。
> 原因有两个，都是用户试用时看出来的：① 它不是按车速分的档，
> 所以阶段模拟的「车速低/中/高」里根本没有它的位置 —— **点不出来**；
> ② 15 km/h/s ≈ 4.2 m/s²，206 CC 自动挡 0-100 约 11s（均值 ≈ 9 km/h/s），
> 实车基本到不了，那张图导进去也永远不亮。
> **只改名不改号**：角色号仍是 8，已经导出的 `image.bin` 不受影响
> （那张图会自然变成"超速"那张；画的内容如果想换，重新导一次即可）。
> 主题里的键名 `eye_surprise` 也保持不变 —— 那是 `theme.json` 的格式，
> 改名会让用户手里的主题静默丢掉这个字段。

- **转速三档按实车地标定**（点火怠速 900 / 稳定巡航 2000 / 表盘上限 7000）。
- **左屏不受车速影响、右屏不受转速影响**。测试把车速从 0 扫到 210 断言左屏不变，
  把转速从怠速 900 扫到表盘上限 7000 断言右屏不变 —— 这条是用户试用时提出来的。
- **水温不参与表情**：它只驱动水温弧和水温数字（那条弧开口朝上，见上面字段说明）。两个原因 ——
  一套水温表情要再加 5 张图（每屏 5 档 × 两屏 = 10 张，经典板 1MB 放不下）；水温是慢变量，
  屏幕下方本来就有弧和数字，再让脸跟着变容易误读（看到"冷车脸"会以为车有问题，
  其实只是刚启动）。
- 曾经还有过「眨眼」和「冷车/过热」，都已删除，编号 11/16 与 14/15/19/20 保留不复用。

**不用凑齐 10 张。** 缺图有**降级链**（`lib/dashcore/face_stages.h` 的
`kFaceFallback`）：运动缺图退巡航、超速缺图退运动……每个状态都一定能退到常态，
一张都没有才回落到程序化占位表情。**左右屏各查各的**：只导入左屏的图时，
右屏仍然走占位表情，不会拿左屏的图顶上。

## 表情阶段模拟（这一页最有用的东西）

页面右下有一块**「表情阶段模拟」**：16 格 = 转速 5 档 + 车速 5 档 + 水温 3 档 +
进气温度 3 档，**每格并排画两块表**（左：转速表 / 右：速度表），下面按屏写明"该用哪张图"：

- 绿色的字 = 用自己那张图
- 橙色的字 = **缺那张图，退到了某张**（例：`左：缺「左屏表情·运动」→ 退到「左屏表情·红区」`）
- 红色的字 = 这一屏一张表情图都没有 → 占位表情

**为什么一格里要放两块表**：两屏是独立状态机，这样一眼就能看出
"点车速档时左屏纹丝不动"—— 只画一块表是看不出来的。

点格子 = 用它当大预览的阶段；上面的「阶段」下拉框可以切 **14 档**，
「左屏表情」「右屏表情」两个下拉框默认"跟随阶段"，也可以**各自单独指定** ——
这就是"独立出表情选项"：左屏只列它自己那 5 个状态（怠速/巡航/运动/高转/红区），
右屏只列它自己那 5 个（静止/市区/快速路/高速/超速）。
**4 个状态对应 4 条阶段用例，所以每个状态都点得出来** ——
旧的"惊喜"是瞬态、表里没有对应的一格，用户试用时问"这个档怎么选不出来"。

> ★ **每组只变自己那一维**：点"速度·中"时**转速表不会跟着动**

## ⚠️ 能放什么、不能放什么（两张分区表不一样大）

> ★ **先选对「目标板」**（图片编辑器右侧「占用」那一栏的下拉框，2026-09-18 加，
> 2026-09-20 加了 240×240 的验证板）：
> | 目标板 | image 分区 | 屏 | 表情画布上限 / 推荐 | 分区表 |
> |---|---|---|---|---|
> | 经典 ESP32（4MB flash） | **1 MB** | 480×480 | 320 / 300（默认给 128，见下） | `partitions.csv` |
> | ESP32-S3 N16R8（16MB flash） | **8 MB** | 480×480 | **320 / 300** | `partitions-s3.csv` |
> | ESP32-S3 微雪双屏（16MB flash） | **8 MB** | **240×240** | **160 / 152** | `partitions-s3.csv` |
>
> 两份表的 theme/image **偏移相同**（`0x254000`）—— 所以刷写命令里**只有
> `--chip` 和"能放多大"两块跟着板子走**（以前这里写"命令一模一样"，
> 加了 240 那块板之后就成了错的：它也是 S3，但 `--chip` 必须是 `esp32s3`）。
> 以前页面把大小写死成 1 MB，于是在 S3 上
> 多出来的 7 MB 根本导出不进去（做大了被浏览器拦下）。现在页面按目标板算，
> 命令行那边加 `--target s3`（240 那块板是 `--target s3_240`）。
> 这两个数字不是抄在 JS 里的：`test-image-blob-build.js` **直接读两份 csv 对账**，
> 分区表改了忘了改编辑器会被测试抓住。
>
> ★ **分区大小与画布上限是两件事**（2026-09-20 分开的）：
> · 分区大小 → "装不装得下"
> · **画布上限 → "画出来的图会不会盖住弧"**，它只跟**屏**有关：
>   240 屏上整套几何是 480 的 0.5 倍，内圈副弧内沿只剩半径 81，
>   所以表情最大 160 —— 按 480 屏的 300×300 做图导进去**不报错**，
>   只是表盘缺一块（这正是这次加 240 档的原因）。
>
> **微雪双屏那块板（240×240）与 S3 那块分区一样大、屏不一样**，
> 所以刷图前先在下拉框里选对板子：选错时页面下面那道「几何闸门」会直接点名。

下面的账按**经典板（1 MB）**算；S3 那块有 8 MB，可以按 240×240 甚至更宽做
（10 张 240×240 = 1690 KB，加满屏背景 2140 KB，余量还很多）。
**240×240 的验证板另有上限：表情 160、推荐 152**（见上面那张表）。

一套完整表情是 **两屏各 5 张 = 10 张** + 背景。

先看单张的账（一张表情 = 宽×高×3 字节，RGB565A8；一张背景 = 宽×高×2 字节），
再按**目标形态**算总数。目标形态默认是"**满屏背景 + 10 张表情**"，
所以下面按 480×480（450 KB）的背景算：

| 单张尺寸 | 一张表情 | 10 张表情 | + 满屏 480 背景 | 1 MB 分区 |
|---|---|---|---|---|
| 192×192 | 108 KB | 1080 KB | 1530 KB | ✗ |
| 152×152 | 68 KB | 680 KB | 1130 KB | ✗ 超 100 KB |
| **134×134** | **52 KB** | **520 KB** | **970 KB** | **✓ 全放下，余 54 KB** |
| 128×128 | 48 KB | 480 KB | 930 KB | ✓ 还能再加别的 |
| 112×112 | 37 KB | 370 KB | 820 KB | ✓ 宽裕 |

- **134×134 是"满屏背景 + 全套 10 张表情"这个形态下的最大尺寸**（经典板 1 MB）。
  ★ 每屏从 4 档变 5 档之后这个上限从 152 降到 134（多两张图就少吃 136 KB）——
  所以**真要用满 5 档，建议直接上 S3**：8 MB 里 240×240 一整套才 2.1 MB。
- 不用满屏背景时（背景只铺弧带以内、或者不要背景图），表情可以放到
  **176×176**（10 张 928 KB）。
- 背景要铺满 480×480 是因为弧带在半径 181..205 —— 一张 240×240 的底图
  离圆心最远才 169.7，**够不到弧带**，那一圈会露出主题底色（这条在
  pcpreview 里逐像素验过，见下面「不上设备也能验证渲染结果」）。

**这是"把状态数压到每屏 5 个"的直接收益**：14 个状态那版无论怎么调尺寸都装不下一整套。

**现实用法（按优先级往里塞）**：

1. **S3 上：满屏背景 480×480（450 KB）+ 10 张 240×240 表情（1690 KB）= 2140 KB**
   —— 一整套齐全，8 MB 里还剩四分之三。**这是推荐形态**。
2. 经典板上：**480 背景 + 10 张 134×134（520 KB）= 970 KB**，刚好放下；
   或者每屏只放「怠速 + 运动」两张：**480 背景 + 4 张 200×200（469 KB）= 920 KB**，
   缺的状态走降级链，不会空白也不会报错。
3. 想要更大的表情或更多状态，就换 S3（16 MB flash）后把
   `image` 分区放大（分区表在 `partitions.csv`，代码不用动）。

编辑器左下有**占用条**，超了会在你点导出前直接报错（不会生成一个会被截断的 bin）。

**导入时的默认输出尺寸 = 原图宽度（上限见上表的「推荐」列，向下取 4 的倍数）**，
也就是**只缩不放**：
- 源图 152×152 → 输出 152×152（**240×240 屏上的推荐尺寸**，也是经典板能装满一套的尺寸）
- 源图 800×800 → 480 屏上输出 300×300（S3）/ 240 屏上输出 152×152（微雪那块板）
- 每张图上会写「原图 WxH　输出 WxH」，**输出比原图大时会标 ⚠ 放大了**，
  超预算时的提示也会点名"哪几张的输出比原图还大"

> ★ 这里踩过一次坑（用户报的）：早先默认输出写死 240，
> 于是按建议做好 8 张 **152×152** 的图导进来会被**放大**成 240×240 ——
> 占用从 542 KB 变成 1350 KB，界面直接报 **132% 溢出**，
> 而缩略图看起来一样大，用户只能看到"我明明做的是 152，怎么还溢出"。
> 现在默认只缩不放，并有 `test-image-blob-build.js` 钉住
> （含"152 的源图输出必须是 152"和"8 张 152 + 480 背景必须装得下"两条）。

### 表情图带透明（已实现，用 RGB565A8）

表情叠在弧线上面，如果是不透明方块会把弧线挡掉一块。所以：

| 角色 | 颜色格式 | 每像素 | 为什么 |
|---|---|---|---|
| 表盘背景 | `RGB565`（`0x12`） | 2 字节 | 铺在最底层，透不透明没意义 |
| **表情（两屏各 5 态）** | **`RGB565A8`（`0x14`）** | **3 字节** | 要叠在弧线上，必须能透出底下的东西 |

"哪些角色算表情"不再手写一串判断，而是问 `face-stages.js`（与固件同源）——
以后加状态不会漏掉某一处、导致新表情丢掉 alpha 通道（那会变成黑边）。

`RGB565A8` 的布局是 **上半部 RGB565 平面 + 下半部独立 A8 平面**
（已在 LVGL 源码 `lv_draw_buf.c` 确认：`size = stride*h + (stride/2)*h`）。
所以它**每像素 3 字节**，不是 2。

**编辑器会自动按角色选格式**：表情图不铺底色、保留 alpha；背景图照旧铺底色合成。
你只要把带透明的 PNG 拖进表情角色就行。

> ⚠️ 改这个格式时**别用 `strideBytes()*h` 算总大小** —— 那不含追加的 alpha 平面，
> 会把合法镜像拒收。用 `ImageView::packedBytes()`。
> 这个坑实际踩过：打包器写 30000 字节、校验按 20000 算，报"尺寸不合法"，
> 而 blob 本身完全正确。现在有 `test_rgb565a8_size_includes_alpha_plane` 钉着。

| 数字读数（第 6 个参数） | 第 140 帧：左屏数字墨迹 x[180..296] y[55..88]、单位 x[223..256] y[104..117]、水温 x[220..259] y[378..390]；右屏**没有**水温数字；开机期间三处命中 0 像素 | 读数画在主题给的位置上、水温只在转速表、开机扫表时数字栏是空的 |
| 缺图降级 | 只导入 3 张老表情时，"运动"显示成红区那张 | 降级链真的按 `kFaceFallback` 在走 |

> 采样点要避开**弧带**（外沿语义下是半径 181..205 那一圈，不是旧文档里的 193..217）
> 和表情的不透明中心，
> 否则读到的是弧线色或表情色，会把正确的图层顺序误判成失败。
> `check-preview-frame.js` 的注释里写了这件事。
>
> 底图铺满之后有个连带效果：**弧的缺口**和**轨道**下面都是底图，
> 所以那两处的期望值是底图色 `#000062` 的混合，不再是被主题底色填的。
>
> 读数那几项用的是**墨迹外接框**而不是单点采样：文本的笔画落在哪个像素
> 取决于字形点阵，采一个点太脆；而"这一带有没有画出足够多的字色像素 +
> 外框落在预期区间"既能证明读出来了，又能挡住一类真错误 ——
> `lv_label_create()` 的**默认文本是 "Text"**，忘了清空时那一带同样是白的，
> 单纯的"有没有亮点"检查发现不了（这个坑真踩过）。

**上传 + 配色两个界面本身已经完成**（`image-editor.html` / `index.html`），
这一轮补的是"固件真的把图画出来"、"表盘上有数字读数"以及
"宿主机能逐像素验证它们画对了"。


表情放在圆弧中间，如果是**不透明的方块**会把底下的弧线挡住一块。
**这条已经解决**：表情现在用 `RGB565A8` 打，alpha 通道保留，由 LVGL 在绘制时混合
（见上面「表情图带透明」一节与宿主机实测结果）。
背景图仍然按"预览底色"合成 —— 它铺在最底层，合成掉反而省 1/3 空间。

### 逐帧满屏开机动画？不要想

480×480 × 12 帧 × 2 屏 = **10.5 MB**，比整块 4 MB flash 还大。
这也是两个 OTA 槽必须等大（各 1 MB）的原因 —— 不能再压缩它们来腾空间了。

## 刷写

```powershell
# 经典 ESP32（4MB flash，partitions.csv）：
$env:PYTHONPATH='C:\Users\Public\206dash\.pio-core\packages\tool-esptoolpy;C:\Users\Public\206dash\stubs;C:\Users\张九思\206Dash\.pio-pylibs'
python -m esptool --chip esp32 --port COM3 --baud 921600 write_flash 0x254000 image.bin
```

| 参数 | 值 | 来源 |
|---|---|---|
| `--chip` | 跟着**目标板**：经典板 `esp32`、S3 两版 `esp32s3` | 页面印的就是对上号的那条 |
| 分区偏移 | `0x254000` | 两份分区表的 `image` 行（故意相同） |
| 分区大小 | 经典板 `0x100000`（1 MB）/ S3 两版 `0x800000`（8 MB） | 同上 |
| 宿主机上限 | `IMAGE_PARTITION_BYTES` | `lib/themetool/image_blob.h` |

> ★ 微雪双屏 240 那块板的完整命令（`--chip esp32s3` + **端口是 COM5** +
> 三路径 `PYTHONPATH`）在本文开头「微雪双屏 240×240」一节的第 4 步，
> 那条是实机验证过的 —— 不要照抄这里的 `--port COM3`（它是占位值）。
> 成功以 esptool 最后一行 `Hash of data verified.` 为准。

刷 1 MB 比刷 128 KB 慢，所以波特率给到 921600（115200 要一分半）。

**没刷过图片也能正常跑**：分区是空的（全 `0xFF`）时，固件解析会失败并
打印 `image: 镜像无效或未刷入,不用图片资源`，然后继续用纯色背景。
这条降级路径和主题一样是刻意设计的。

## 生成的二进制格式

```
偏移 0     : 镜像头 1420 字节
             +0  magic   = 0x44363032 ('206D')
             +4  version = 1
             +6  count   = 图片张数 (≤32)
             +8  data_bytes
             +12 索引表: 每项 44 字节 × 32
偏移 1420  : 像素数据（按索引表的 offset/size 排布）
```

索引项 44 字节 —— **没有任何对齐空洞**，每个字段都紧跟前一个：

| 项内偏移 | 字段 | 类型 |
|---|---|---|
| 0 | `offset` | u32（相对数据区起点） |
| 4 | `size` | u32 |
| 8 | `w` | u16 |
| 10 | `h` | u16 |
| 12 | `cf` | u8（LVGL 颜色格式，`0x12` = RGB565） |
| 13 | `stride_pad` | u8 |
| 14 | `role` | u16 |
| 16 | `order` | u16 |
| 18 | `name[24]` | char（必须留 `'\0'`） |

44 = 4+4+2+2+1+1+2+2+24，正好是 4 的倍数，所以尾部也不用填充。

> **`offset` 是 u32，这一条很关键。** 它曾经是 u16，把整个镜像的像素数据
> 卡在 64 KB 以内 —— 一张 480×480 背景就要 450 KB，1 MB 的分区等于白给。
> 更麻烦的是不报错：偏移溢出后设备端拿到错误的像素位置，画面是花的，
> 但日志一切正常。
>
> 另外，**别手算结构体对齐**。这里踩过两次：一次漏算了两个 u32 之间的洞，
> 一次多算了尾部填充。现在 C 侧有一条 `offsetof`/`sizeof` 断言
> （`test_entry_field_offsets`），JS 侧有"头部字段"一节，两边把同一张表
> 各钉一遍，往返测试再逐字节对账。

像素是 **RGB565 小端**（低字节在前）。写反了画面会"红蓝互换 + 竖条纹"。

## 改格式时怎么保证两边不跑偏

这个格式由**两套代码**共同维护，改错一处编译期完全看不出来：

- 生成方：`image-blob-build.js`（网页和 Node 都用它）
- 读取方：`lib/themetool/image_blob.cpp`（ESP32 固件）

所以有一个自动核对，**提交前跑一次**：

```powershell
pwsh tools/theme-editor/test-image-roundtrip.ps1
```

它做三件事：

1. Node 侧打包器单测（357 项断言：字节序、stride、对齐空洞、名字截断、坏输入必须报错、
   240 档的画布上限与 `spec-240.json` 的总字节数）
2. 用 JS 打一个测试镜像 `.pio/image-test/image.bin`（同时生成可读的 `.manifest` 对账清单）
3. 跑 `pio test -e native`，让**固件自己的解析器**读这个镜像，逐字段、逐字节对账

这个核对抓出过两个真 bug（写索引项时用了上一轮循环遗留的变量，导致每项名字都相同；
像素循环漏了 x 偏移，导致每行重复第一个像素）—— 都是编译通过、肉眼看不出来的那种。

## 表盘朝向也要对账（`test-gauge-geometry.js`）

```powershell
node tools/theme-editor/test-gauge-geometry.js   # 71 项断言
```

管两件事：

1. **两个编辑器的角度换算不加任何偏移**。LVGL 的 `lv_arc` 是 0°=3 点钟、顺时针，
   而 canvas 的 `arc()` 约定完全一样 —— 所以 `d` 直接换成弧度即可。
   曾经两个页面都写成 `(d - 90)`，于是预览里的表**整体被逆时针转了 90°**：
   起点从 7:30 跑到 4:30、缺口从正下方跑到正右方。固件一直是对的，
   但用户先看到的是预览，于是问"表的方向是否需要向右旋转 90 度"。
2. **默认主题的满量程弧缺口在正下方**、起点在左下（135°）、`end > start`（顺时针增长）、
   内圈半径小于外圈、两条弧开口方向相反 —— 都是**产品决定**，写错了不报错、只是"看着怪"。

固件那一侧的朝向由 `check-preview-frame.js` 的「表盘朝向」检查兜着：
它读**真实落帧**，沿弧带扫一圈断言"正下方是缺口、正上方有弧"。

## 表情阶段表也要对账（`test-face-stages.js`）

```powershell
node tools/theme-editor/test-face-stages.js     # 429 项断言
```

它**解析 `lib/dashcore/face_stages.h` 的源码文本**（14 条阶段用例、缺图降级链、
槽位→角色编号三张表），与本目录的 `face-stages.js` 逐字段比对，
再和 `image-blob-build.js` 的角色编号比对一遍。

为什么值得单独一条：表情导入页的"阶段模拟"会告诉用户
"转速·中 = 左屏巡航脸、右屏常态脸"—— 这是刷图之前**唯一**能看到的证据。
网页那份表和固件那份不一致，预览就是在骗人，而真车上的表现要等刷完图才知道。

## 页面本身也要检查语法（`syntax-check-pages.js`）

```powershell
node tools/theme-editor/syntax-check-pages.js
node tools/theme-editor/test-theme-json.js
```

两个编辑器是**双击打开的静态 HTML**：没有构建、没有 lint，
语法错误的表现是"页面一片空白"或"点了没反应"，而不是一条报错。
这个脚本把每个内联 `<script>` 的正文交给 `new Function` 编译（不执行），
并检查 `<script>` 开合是否配对、引用的本地 `.js` 是否存在。
最后那条是踩过坑才加的：曾在页面中间多出一个 `</script>`，
后面几百行 JS 全跑到标签外面 —— 表现是空白页，而"每段脚本都能编译"的检查
完全查不出来（它们确实都能编译）。

`test-theme-json.js` 管的是另一件事：主题文件里的 `0xRRGGBB` 颜色，以及
**默认主题三处副本的一致性**。前者固件读得懂、而 `JSON.parse` 读不懂 ——
这条曾经让"导入 theme-default.json"直接报一句和颜色毫无关系的语法错。
它同时用真实的 `theme-default.json` 做回归，并断言"直接 JSON.parse 确实会失败"，
免得测试自己变成空转。

三处副本是：`lib/themetool/ui_theme.h` 的 `theme_set_defaults()`（固件的事实来源）、
`theme-default.json`（给人当模板）、`image-editor.html` 的 `ARC_FALLBACK`
（图片编辑器没读主题时的兜底弧）。它们不一致**不会报错**，只会表现成
"预览颜色不对"或者"照参考文件刷进去两个表左右颠倒"—— 后者真实发生过。

**读数颜色那一节（2026-09 加的）也是同一套对账**，而且副本更多：
除了上面三处里的四个颜色，图片编辑器还有**预览用的位置表**（`READOUT_LAYOUT`）
与**字号表**（`READOUT_FONT_PX`，480 → 48/18、240 → 24/10）——
这两份不写进主题文件，只决定"预览画在哪、多大"，抄错了就变成
"预览里的字和真车不是一个位置/字号"。所以 `test-theme-json.js` 里那一节
**把页面自己的函数抠出来真跑一遍**（`ensureReadout` / `readoutLayout` /
`readoutFontPx` / `readoutText` / `unitText` / `drawReadout` …，用 `new Function`
注入 `previewSide()` 与 `gTheme`），拿一个记账用的假 canvas 收 `fillText`，
断言：四个颜色改了预览里就跟着变、字号在 480/240/200 宽小图上各是多少（
字号被"缩两次"过的那个 bug 就是这么钉住的）、`show_*` 关掉就不画、
老主题（没有 `readout`）补上的就是固件默认色。

## 范围与限制

**已实现**：图片导入（PNG/JPG/WebP）、三种缩放方式、用途与顺序、双屏合成预览、
导出 `image.bin`、导出 C 数组、占用预算提示、格式一致性自动核对、
**表情透明（RGB565A8）**、**固件真的把图画出来（背景在弧线下、表情在最上层、
两屏各取自己那一套）**、**每屏 5 个状态各一张图 + 缺图降级链**、
**两屏独立的表情（左看转速、右看车速，水温不参与）**、
**表情阶段模拟（10 档、一格并排两块表、"缺图退到哪张"、左右屏可各自指定表情）**、
**表盘数字读数（大数字 + 单位 + 水温/进气温度，主题里可调；图片编辑器里也能改颜色）**、
**宿主机逐像素验证渲染结果**。

**还没做**：

- **真屏本身**。渲染逻辑、图层顺序、透明混合、读数位置都已经在 `pcpreview` 里
  逐像素验过了，但屏幕的分辨率/色深/驱动时序要等屏到货（改 `ui_theme.h` 的
  `THEME_DISPLAY_RES` → 写实驱动 → 最后才删 `DASH_DISPLAY_STUB`）。
- **开机动画换图**：你已确认**不做逐帧**，所以开机画面走程序化扫表
  （淡入 + 扫表 + 表情显形），"显形"的透明度切换对图片表情也生效
  （已实测：前 5 帧表情透明、之后可见）。
- **眨眼/定时表情**：`Blink` 状态已删除（与车速/转速/水温无关，也讲不出
  什么工况会触发）。稳态表情**只由数据决定、与时间无关** —— 这一点有单测钉住。
  要做"眼皮动"这类动作得引入多帧序列，目前没这个需求。
- **声音告警段（排队中；规格与分区算术见 `ACCEPTANCE.md` 的 2026-09-20 条）**：
  `image-editor.html` 以后加一块「声音」区 —— 拖 WAV 进来、**在浏览器里直接试听**、选它绑哪个条件
  （转速进红区 5800 / 超速 >130 …），控件旁**就地写明格式与上限**（WAV / PCM / 16-bit / 单声道 /
  8~16 kHz，单文件 ≤3 秒且 ≤96000 字节）。不传就是固件合成的三短音（零素材、零分区占用），上传只是覆盖。
- **1 MB 装不下"满屏 480 背景 + 240×240 全套 8 张表情"**（见上面那节）。
  满屏背景的形态下表情上限是 **152×152**（8 张 + 背景 = 993 KB）；
  不要满屏背景时可以放到 192×192（甚至 208×208）。换 S3 后放大 `image` 分区即可。

# 车主模式（2026-10-15）

编辑器（`tools/theme-editor/index.html`）现在**默认进入车主模式**。

★ **2026-10-15（同一天，车主口径变更）：配色页与图片页合并成一个页面。**
车主原话：「图片页和配色页能合并吗，因为感觉功能上其实是统一的。」
⇒ 现在只有 `index.html` 一份实现，里面是**两个页内分区**：
「① 配色」与「② 图片」，**共用同一份主题状态 `T` 与同一份图片清单 `items`**。
`image-editor.html` 只剩一个跳 `index.html#images` 的**重定向薄壳**
（几行、没有脚本），老书签仍然能用，但**没有第二份实现**。

这一页只回答三件事：**车主默认看到什么**、**框选怎么工作**、
**为什么"产物逐字节兼容"这句话是可信的**。

## 1. 车主模式里有什么（默认）

顶栏下面那条「分区」标签切两半（高级模式下它藏起来，因为高级本来就把两边放在一起）：

| 分区 | 控件 | 备注 |
|---|---|---|
| **① 配色** | **背景色**、**四条弧的点亮色**、**数字颜色** | 共 6 个色块；水温/进气的副表颜色、轨道色、单位色在「高级」里 |
| **① 配色** | **红区转速 rpm**、**超速 km/h** | 两个阈值**仍然生效**（弧染红 / 大数字变红 / 脸变红） |
| **① 配色** | 3 个**配色预设**：当前默认 / 夜间 / 浅底 | 写进**当前主题状态**（导出的还是同一份 `theme.json`，不新造格式） |
| **② 图片** | ★★ **槽位清单**：背景 1 格 + 表情 10 格 | 见下面 §1.1；每格「名称 + 缩略图 + 换图/清除」 |
| **两边都有** | **保存安装包（assets.bin）** + **一条**刷写命令 | **端口可改、偏移不让改**（写死 `0x210000`，取自分区表）。两个按钮调的是**同一个** `saveOwnerPackage()`；两个端口框是**同一个值** |
| 右栏（共用） | 左右两块预览画布 + 阶段预览 + 开机动画 + 表情阶段模拟 | 两个分区看的是**同一张画布、同一条渲染路径** |

预设里的「当前默认」是从 `defaultTheme()` 取的，不是抄一份数字 —— 固件默认值改了它跟着走。

### 1.1 ★★ 槽位清单（2026-10-15 车主实测反馈后加）

车主原话：**「图片列表应该放到车主模式那边，不然没办法对全部表情和背景进行编辑。」**

⇒ 「② 图片」分区里**直接给出全部 11 个槽位**，一格一行：

| 格 | 名称（中文阶段名，来自 `face-stages.js`） | 拖入/选文件时 |
|---|---|---|
| 1 | **背景**（两屏共用，铺满 480×480） | **不弹框选**；可用 JPEG；走 `addFiles(files, ROLE.Background)` |
| 2–6 | **左屏 · 转速表（+水温）** · 怠速 / 巡航 / 运动 / 高转 / 红区 | **弹框选**（方框 = 保留区）；必须带 alpha（PNG） |
| 7–11 | **右屏 · 速度表（+进气温度）** · 静止 / 市区 / 快速路 / 高速 / 超速 | 同上 |

每格三件事：**名称**（+ 当前那张的文件名/尺寸/格式，或"空"的说明）、**缩略图**（棋盘格 = 透明）、
**「选文件 / 换图」+「清除」**两个按钮。拖到某一格会高亮那一格，松手就进那一格。

* **背景 1 个 + 表情 10 个**这两个数是**算出来的**，不是写着好看的：
  `ownerSlotSpecs()` = 背景那一格 `.concat(faceSlots())`，而 `faceSlots()` 是
  遍历 `FaceStages.statesOf(0|1)` 得来的 ⇒ 固件那边加了档位，这里自动多一格。
* **名称不用 role 编号**：`"左屏 · 转速表（+水温） · 怠速"` 这样拼出来的
  （`FaceStages.screen(s).label` + `st.label`），所以"哪一格是哪块屏"从名字上就看得见。
* **技术参数不进车主模式**：`contain`/`cover`/`stretch`、裁透明边、目标宽度、播放顺序
  仍然**只在「高级 → 图片列表」**里（车主要求"车主模式保持干净"）。
  车主模式里只有一句**指路文字**说"技术参数在高级"，那不是控件 ——
  `check-owner-mode.js` 只查控件（`input`/`select`/`button`/`label`），不查封面的说明。
* **换图必须真的换掉**：同 role 再进来一张时，旧的会被挪到 `order` 后面
  （设备端按 `order` **最小**的那张取用）—— 否则车主换了图却看不到变化。
  框选确认（`cropConfirm()`）与普通导入（`addFiles()`）**两条路都做了这件事**。
* **清除**按 role 把这**一个槽位上所有**图删掉（同 role 多张时一次清干净），
  空格子的「清除」按钮是禁用的。
* 「＋ 加一张」仍然是老路径（按「高级」里的用途规则自动归类），
  给"我就是要随便塞一张进去"留个口子。

> **配色与图片为什么能合成一页而不出"两个真相"**：合并前是两页各持一份主题对象、
> 靠"同一个 localStorage 键 + 跨页再读一遍"保持同步；合并后**物理上只有一个
> `T` 对象、一份 `items`**，切分区只切显隐（`applyPart()`）。
> 连"框选好的那张交给另一页"那套中间状态（`206dash.faceHandoff`）也删掉了 ——
> 框选结果直接 `items.push()` 进**那一格**。

### 高级里保住了什么（一个都没删）

点顶栏的「高级」（两个分区的东西这时都在同一栏里）：

* **配色那一套**：恢复默认 / 导入主题文件 / 导出 theme.json、**主题 JSON 文本框**（只在高级里）、
  以及原来那一整面控件墙 ——
  表情大小/底色/五官色、每条弧的起始角/结束角/半径/线宽/轨道色/轨道透明/涨幅反向、
  水温量程/进气量程、数字与单位的颜色/字号/中心 y/显示开关、开机动画的 8 个毫秒、
  告警那一组（超速/迟滞/红区/迟滞/转向忘关/门去抖/通用去抖/响一声/最短间隔/只报最高优先级）。
* **图片那一套**：图片列表 + 用途/顺序/缩放方式（`contain`/`cover`/`stretch`）/裁透明边/目标宽度、
  弧与读数的全部颜色编辑器、导出 theme.json / 读入 theme.json·assets.bin / 用固件默认、
  导出 image.bin / 导出 assets.bin、刷写那一栏（cmd + 复制 + 导出 C 数组 + 载入已有 bin）、
  占用（目标板 + 预算条）。

两个模式**共用同一份状态**：切模式只切显隐，不产生第二份主题。模式与分区各记在
`206dash.themeEditorMode` / `206dash.themeEditorPart`（与配色那份 `206dash.theme` **分开** ——
本机偏好不进导出的主题）。端口在 `206dash.flashPort`、预览尺寸在 `206dash.previewZoom`。

## 2. 框选器（两种语义：表情"框选"、背景"取景"）

在「② 图片」分区里，点某一格的「选文件 / 换图」（或把图拖到那一格）→ 弹框选。

### 2.1 表情：方框内 = 保留区

* **方框内 = 保留区**；框外用半透明黑压住（"框外丢掉"看得见）。
* **拖动 = 平移**（指针事件，鼠标与单指都走它）。
* **滚轮 = 缩放**，以指针位置为不动点；**双指捏合**同样缩放（触摸屏）；滑杆也能缩。
* 确认后导出一张**方图**：主体居中、**四周透明**（画布不铺底色 ⇒ 天然带 alpha）。
* 上限/推荐值**问 `ImageBlob`**（480 档 320 / 300），页面里不写死。

### 2.2 ★★ 背景：取景框（cover 语义）—— 2026-10-15 车主实测反馈后加

车主原话：**「主题背景图这边导入没有框选选项」**。

> ★ 这条**推翻了**最早"只给表情槽做框选、背景不加框"那条口径。
> 但背景的语义**与表情不同**，不是照抄一份：

| | 表情（mode="face"） | 背景（mode="bg"） |
|---|---|---|
| 方框的含义 | **保留区**（框外丢掉 → 透明） | **取景区**（框内就是最终画面） |
| 图与框的关系 | 不限（框外本来就丢） | **图必须盖满整个框**（不露底） |
| 可用格式 | PNG / 带 alpha 的 WebP（**必须真有 alpha**） | PNG / JPEG / WebP（**不要求 alpha**） |
| 产物 | 方图，四周透明 ⇒ RGB565A8，上限 320 | 方图，铺满 ⇒ RGB565，整屏 **480×480** |
| 进槽 | 既有 `renderToTarget` 的 **contain** 分支 | 既有 `renderToTarget` 的 **cover** 分支 |

交互与表情**完全同一套**（同一个框选器组件、同一份平移/缩放数学）：拖动平移、
滚轮/双指缩放；**缩放下限就是"刚好盖满"**（再往外缩框内就露底了），
所以框里永远只有照片本身；确认后按 cover 输出，**边长对齐到 4**。

### 2.3 两条边界（都要紧）

1. **框选只影响"进槽之前的像素"。** 产物是一张普通 `canvas`，之后走的是**既有**那条路：
   `renderToTarget()`（contain / cover、只缩不放、保持比例、居中）→
   `ImageBlob.rgbaToRgb565A8()`（背景是 `rgbaToRgb565()`）→ `ImageBlob.build()`。
   框选器**不自己编码**，也不碰包头 —— `image.bin`/`assets.bin` 的字节布局**一个字都没动**。
2. **不改任何容器格式**：WebP 只出现在"**进槽前的解码**"这一步（见 §2.6）。

### 2.4 ★★ 表情"不够居中"那条（2026-10-15 车主实测反馈）

车主原话：**「表情图片现在导入位置好像不够居中」**。

**根因是"框选器一打开给的那个构图"，不是产物管线。** 查证过程与结论：

* 把「框选 → `renderToTarget(contain)` → `rgbaToRgb565A8`」逐段量过（Node 侧的
  canvas 替身 + 页面里的**真函数**）：`renderToTarget` 与内核编码**都没有平移错**
  （300 与 320 两种尺寸下，非透明像素的包围盒中心都落在画布正中）。
* 错在 `cropFit()` 的**第一版**：它把方框开成 `min(面板, 图片)` 那么大 ——
  源图是正方形时**框 ≈ 整张图**，于是"框内那一片"就是整张图，主体在图里偏多少、
  产物里就偏多少；而且框已经占满画布 ⇒ **一点都拖不动**，车主想自己挪都挪不了。
  他看到的"不居中"就是**一打开那个偏掉的构图**，加上框又不动。
* 修法（`cropFit()` 现在的三条约束）：① 框内源像素 ≥ `目标边长 × CROP_FILL(0.8)`，
  **并且 ≤ 主体包围盒的 2 倍**（框贴着主体 ⇒ 主体落在正中，要留白自己往外滚）；
  ② 框装得进图（`F/k ≤ min(sw,sh)`）⇒ 能拖动取景；③ `k ≥ 1`（不放大源图）；
  取景面板做成**正方形**（框与面板对齐，"框就是你看到的那一块"）。
* 可复现的判据：`check-crop-centering.js` 用一个**明显偏心**的主体
  （360×360 图、圆心在 (130,120)），跑真管线，断言**产物里非透明像素的包围盒中心
  落在目标画布中心 ±1 px**（现在实测偏移 **0.00 px**）；另有一段**反向对照**，
  证明"把框对回图片中心会明显偏"⇒ 这条断言不是空转。

> ★ "产物错了"还是"预览显示错了"？—— 都不是"画错"，而是**初始构图**错了
> （框太大、又拖不动）。预览与产物本来就是一套坐标（框内就是产出的那一片），
> 改的是"一打开给哪个框"。

### 2.5 跨页交接

在配色分区的表情格里框选好的那张方图，会以一张 data URL 存进 `206dash.faceHandoff`，
然后切到「② 图片」分区；图片分区启动时接住它、按选好的 role 作为一条普通 item 进列表。
**它只是一张待进槽的方图，不是第二份主题状态**（主题只有 `206dash.theme` 那一份）。

### 2.6 ★★ WebP（2026-10-15 车主给了 .webp 素材）

* **浏览器天然会解 WebP**（`new Image()`）⇒ 走**既有 canvas 路径**：
  解码 → 画到 canvas → 按既有规则产出。**没有自己写编解码**。
* **背景槽**：WebP 允许（与 JPEG 同理，不要求 alpha）。
* **表情槽**：WebP **也允许**，但**必须真的有 alpha** —— 解码后**读像素**量一遍
  （`measureAlpha()`：有没有 `alpha < 255` 的像素），把结果交给 `asset-spec.checkUpload()`
  的**同一份判据**回答收不收。全不透明 ⇒ 按现有规则拒绝，文案：
  「…解出来的**每个像素都是不透明的**（alpha 全是 255，实测 min=255 / max=255）…
  ★ 表情要透明背景，请用 PNG 或带透明的 WebP。」
* 判据的去向没变：`asset-spec.js` 的 `checkUpload()` 仍然回答"收不收、为什么"，
  页面只负责**量**（`opts.alpha = { has, min, max }`）。**不传 opts 时行为与以前一字不差**，
  所以命令行/文档/既有测试那些老调用点不受影响。
* **不改任何容器格式**：WebP 只在"进槽前的解码"出现，`image.bin`/`assets.bin` 一个字节没动。

### JPEG / 没有 alpha 的 WebP 会被拒绝

规则与文案的唯一权威是 `asset-spec.js` 的 `checkUpload()`：表情槽 `alpha: "required"`，
JPEG 没有 alpha ⇒ 报错；WebP 格式上"可以带 alpha"，但**解码后像素全 255 一样拒**。
两种情形的提示都会点到 **「表情要透明背景，请用 PNG」**（WebP 那条会补一句"或带透明的 WebP"）。

## 3. 「产物逐字节兼容」的证据

**声明**：这一单没有改任何输出格式 —— `theme.json` / `image.bin` / `assets.bin` 的字节布局一律没动，
`theme-json.js`、`image-blob-build.js`、`asset-package-core.js` 的产物与改动前**逐字节相同**。

**证据**（可复跑，不是"我看着没改"）：

```bash
# 1) 产出/核对"打包产物指纹"（固定输入 → 三段打包 → SHA-256）
node tools/theme-editor/make-golden-hashes.js            # 写入 .golden-hashes.json
node tools/theme-editor/make-golden-hashes.js --print    # 只打印，不写文件

# 2) 指纹比对（check-owner-mode.js 的第 ⑬ 节）
node tools/theme-editor/check-owner-mode.js
```

指纹里各是什么：

| 字段 | 含义 |
|---|---|
| `themeJsonSha256` | `index.html` 的 `defaultTheme()` 按 `JSON.stringify({theme:T},null,2)` 序列化后的 SHA-256 |
| `imageEditorThemeJsonSha256` | `ARC_FALLBACK`（合并前在图片页，现在并进 `index.html`）同样序列化后的 SHA-256 |
| `imageBinSha256` | 固定图案（一张 RGB565 背景 + 一张 RGB565A8 表情）打成 `image.bin` 的 SHA-256 |
| `assetsBinSha256` | 上面两者经 `AssetPackageCore.packBytes()` 合成容器的 SHA-256 |
| `assetsBinImagePageThemeSha256` | 换用 `ARC_FALLBACK` 那份主题再合成一遍的 SHA-256（两种默认主题都在指纹里） |

**合并前后的实测值完全相同**（这一单的收尾验证）：

```

themeJsonSha256                   2cf2c42432c211fb62aa05252a47ad7576278f2983e1f1bc5db67e3da439445b
imageEditorThemeJsonBytes         1389
imageEditorThemeJsonSha256        5fdfd1b262ec37038f74e8cb2d79b13c19dff11b17d8a8fee1c8ed4b8b5f2bdc
imageBinBytes                     16524
imageBinSha256                    24fc3c873d5c5641720f687f2edfd719d525db0f361ba23f357b40679dda783c
assetsBinBytes                    295052
assetsBinSha256                   63fe3276be21c5cebd1031dcfcdbab8ff1806dd19f2fb1869655863663293271
assetsBinImagePageThemeBytes      295052
assetsBinImagePageThemeSha256     c99766402ccf996923a7897c798929d465ca47f4130eea1a602cbe7be7e75351
```

★ **输入是算出来的**：主题字节从页面源码里把 `defaultTheme()` / `ARC_FALLBACK` 抠出来求值，
图案是纯函数 —— 不读 `theme.json` / `local/*.bin` 那些本机文件，所以换台机器哈希也一样。

★ 指纹**只能说明"这一段代码的产物没变"**：它证明不了"框选器写的像素对"。
像素那一层的判据是 `smoke-pages.js`（页面能跑起来）+ `check-owner-mode.js` 第 ⑦ 节
（框选结果确实作为普通 item 交给既有那条路）。

## 4. 这一单新增的测试（都进 CI/手工跑的那一套）

| 脚本 | 判什么 |
|---|---|

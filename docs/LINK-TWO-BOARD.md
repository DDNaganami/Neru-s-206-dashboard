# 双板链路 v1 —— **两块板对打**怎么做（两块 2.8C，需要第二块板）

**这份文档是什么**：把 `lib/link`（双板链路协议 v1）在**两块**微雪 `ESP32-S3-LCD-2.8C`
上跑通的台面操作步骤 —— 接线、烧写顺序、命令、期望输出、每一行的含义、**它测不到什么**，
以及 §8 L1 那三条残余待确认（ⓐⓑⓒ）最小的实测办法。
契约在 `ARCHITECTURE.md` 的「## 双板链路协议 v1 范围」；本文只讲怎么**动手**。

适用固件：**两个角色镜像**（`platformio.ini` 里新增的两个 env，都 extends
`[env:esp32s3-rgb]` ⇒ 都是 2.8C 显示固件，面板/守护/蜂鸣器/诊断页全在）：

| 角色 | env | 关键 `-D` | 它做什么 |
|---|---|---|---|
| **主板（A / 右板）** | `env:esp32s3-rgb-master` | `-DLINK_ROLE=1` `-DLINK_PHY_UART=1` | 发 `TICK`(50 Hz)/`HELLO`/`DATA`(≤80 Hz)；收 B 的 `STATUS`/`EVENT`（**只进日志**，§3 单一日志出口） |
| **从板（B / 左板）** | `env:esp32s3-rgb-slave` | `-DLINK_PHY_UART=1`（角色走 `link_role.h` 的**默认值 0**） | 收 A 的 `TICK`(喂 §4 时基)/`DATA`(喂数据层，来源变 `FieldSource::Link`)；今天不发帧 |

### ★★★ 一眼分清手里这块板是哪一角色（2026-09-25 新增，车主的需求）

两块 2.8C **外观完全一样**，而角色是**编译期**定死的（§5：运行期没有任何代码能改它）
⇒ "这块板是谁"只存在于刷进去的那份固件里。所以现在**三处**都自报家门（**全部纯 ASCII**
—— 本构建只使能 Montserrat，中文**一个字形都画不出来**）：

| 在哪 | 长什么样 | 活多久 |
|---|---|---|
| **开机时的屏幕**（最有用） | 屏上两行大字：`MASTER (RIGHT)` / `esp32s3-rgb-master`（从板是 `SLAVE (LEFT)` / `esp32s3-rgb-slave`） | **只在开机动画那一秒多里**（`BOOT_TOTAL_MS`），动画一结束就消失 ⇒ 表盘保持干净 |

## 1. 接线（**4 根线，其中只有 2 根是信号**）

```
   ┌──── 主板 A（右，env:esp32s3-rgb-master）────┐        ┌──── 从板 B（左，env:esp32s3-rgb-slave）────┐
   │                                             │        │                                             │
   │  12PIN TXD  = GPIO43 (UART0 TX) ●───────────┼────────┼──────● GPIO44 (UART0 RX) = 12PIN RXD        │
   │  12PIN RXD  = GPIO44 (UART0 RX) ●───────────┼────────┼──────● GPIO43 (UART0 TX) = 12PIN TXD        │
   │  12PIN GND  ────────────────────────────────┼────────┼────── 12PIN GND              ← ★ 必接       │
   │  12PIN VBUS(5V) ────────────────────────────┼────────┼────── 12PIN VBUS(5V)  ← ★ 只由 A 一边供    │
   │                                             │        │                                             │
   │  ★ 3V3 一个都不要接（两块板各吃自己的 LDO）   │        │  ★ 也不要把两边的 5V 对插（见下）           │
   └─────────────────────────────────────────────┘        └─────────────────────────────────────────────┘
                每块板都是「43 发、44 收」⇒ 线是**交叉**的：A.43 ↔ B.44、A.44 ↔ B.43
```

| 项 | 值 | 为什么 |
|---|---|---|
| **A.43 → B.44** | 11 根杜邦线里的一根（母-母） | §0「本节对「接线定案」的一处新增」：A→B 的主流量（`TICK`/`DATA`） |
| **B.43 → A.44** | 另一根 | B→A 的次流量（`STATUS`/`EVENT`）—— ★ **两根都要接**（v1 是双向的；只接一根的话主板那 30 s 的 `从板无响应` 会一直报） |
| **GND ↔ GND** | 第三根 | **既当电源回流、又当信号地**（就这一根）—— 不共地 = 线上电平没有共同参考点，症状是 `crc_err` 涨或干脆收不到 |
| **5V ↔ 5V** | 第四根，**只由主板（A）的 12PIN `VBUS(5V)` 送过去** | 从板由主板供电（§0「线缆」）。★ **两块板各自插着自己的 USB-C 时，这一根先别接**（见下面的⚠） |
| **3V3** | ★★ **绝不接**（两端都不接） | 每块板自己的 LDO 管自己那一路；跨板送 3V3 = 一块 LDO 扛两个负载 **+ 倒灌**（§0 原话） |
| 波特率 | **115200 8N1** | §1.1（`dashlink::kLinkBaud`，`lib/link/link_phy_pins.h`） |

### ⚠ 三条会烧东西 / 会让结果不可信的注意

1. ★★ **两块板同时插着 USB-C、又接了 5V 那根线 = 两个 5V 源对顶**。
   台面上请二选一：**要么两块板各插各的 USB-C（这时不接 5V 那根）**，
   **要么只由 A 的 12PIN 送 5V（B 的 USB-C 拔掉）**。本流程（§3）走的是前者 + 后者交替。
2. ★ **`5V` 排针出厂状态不一定是 5V**（`PINOUT.md`「开箱当天」那条警告 + §8 L7）——
   第一次接从板之前，**先用万用表量 A 板 12PIN 那个 `VBUS(5V)` 脚对 GND 的电压**，
   确认是 4.8~5.2 V 再接线。量出来不是 5V 就先别接（那条 L7 到今天还开着）。
3. ★ **别去碰 GPIO0**（12PIN 上有它）：它同时是 **BOOT strap** 与那颗 `FSUSB42UMX`
   的 `SEL`（§8 L1）—— 拉错电平会把 43/44 从排针切到 CH343P，链路**静默失效**。

### ★★ 为什么 43/44 不是"随便挑的两个脚"

契约 §0「载体」：链路用的就是 **UART0 的那一对脚**。而在这块板上，43/44 上还挂着一颗
**`FSUSB42UMX`（2:1 模拟开关，§8 L1）**，把 `IO43/IO44` 在 **CH343P（板载 USB-串口桥）**
与**排针**之间**二选一**：

* **插上 UART Type-C ⇒ 4Pin UART（含 12PIN 的 TXD/RXD）被禁用**（wiki 原话；
  `ARCHITECTURE.md` §8 L1 已按官方原理图逐脚读出）；
* **拔掉 UART Type-C ⇒ 4Pin UART 才通**。

⇒ 这条就是 §2 与 §3 的**全部理由**：**刷机（插 Type-C）与跑链路（拔 Type-C）天然互斥**，
不可能边刷边跑。而从板那一侧的降级路径（>500 ms 冻结最后值、>3 s 回退 Sim，§7）会照常走完。

## 2. ★★ 链路固件下"日志在哪"：只走原生 USB-CDC（19/20），只在 12PIN 上

这是本单**最容易误判成"板子坏了"**的一条，写在最显眼处：

| 固件 | 日志走哪 | 那个口在哪 | 台面上怎么够得着 |
|---|---|---|---|
| `env:esp32s3-rgb`（**不带**链路 PHY） | **两个都发**：UART0（43/44 = CH343P = Type-C = `COMx`）**+** 原生 USB-CDC | Type-C 就在板上 | 插 Type-C，`pio device monitor` 直接看 —— 这是**今天已经在用**的那条 |
| `env:esp32s3-rgb-master` / `-slave`（**带**链路 PHY） | ★ **只有原生 USB-CDC（GPIO19/20）** | ★ **只在 12PIN 排针上**（`D-`/`D+` / wiki 叫 `USB_DP`/`USB_DM`） | **要引线**，见下面两条办法 |

### ① 只想要日志：把 12PIN 的 19/20/5V/GND 引到一根废 USB 线

原生 USB 是**芯片内部自带**的 USB 控制器（USB-Serial-JTAG），只要 `D+`/`D-` 两根数据线
接到一个 USB 口就能被 PC 认出来（板子上那颗 Type-C **与此无关**）。做法：

```
   12PIN:  5V   →  废 USB 线的 VBUS(红)   ← ★ 注意极性/顺序，接错会灌进 LDO
   12PIN: GND   →  废 USB 线的 GND (黑)
   12PIN: D- (GPIO19) → USB 线的 D- (白)
   12PIN: D+ (GPIO20) → USB 线的 D+ (绿)
```

* 只有**原生 USB 控制器**那一路会在 PC 上出现一个新的 COM 口（本机实测过：VID `303A`，
  USB-Serial-JTAG）—— 它就是链路固件唯一的日志出口；
* ★ 那根废 USB 线**不要剪掉另一头**：插到 PC 的一个 USB 口上；若走的是"A 板 12PIN 送 5V
  给 B"的接法，**这根线的 VBUS 就别接**（只接 GND/D+/D-），否则又是两个 5V 源对顶。
* ★ **顺序**：先接 GND，再接 D-/D+，最后才是 5V（或干脆不接 5V，让板子由 Type-C 或
  A 板的 12PIN 供电）。

### ② 想要"电和日志同时有"又不想动烙铁：**两块板交替接**

本流程（§3）用的就是这个，**零额外材料**：

1. 烧机时：每块板插**自己的 Type-C**（电 + 刷写 + 那几行能看见的日志都是它）；
2. 跑链路时：两块板的 Type-C **都拔掉**（43/44 这才归 4Pin），电由 **A 板 12PIN 的 5V**
   送给 B；
3. 要看哪块板的日志，就**只给那一块板**插上 Type-C —— 但记住：**它一插上，它自己那
   43/44 就被切到 CH343P 了**（§1 那条），也就是**它会立刻从链路上掉下来**。
   ⇒ 这是"看一块的日志"的代价，**不是**"边看边跑"的办法。
   ★ 真要边看边跑，只能用 ① 那条引线（把 19/20 引出来），日志口与链路口才是**两个**口。

> ★ 判据上的一条便利：主板侧那行 `link: tx=… rx_ok=… crc=… role=… B 在线/从板无响应`
> 每秒都打一次，**只看主板一个口**就能同时看到 A 与 B 的关键状态（§3 的"单一日志出口"）。

## 3. 烧写顺序（**一次只插一块板**，别跳步）

> ★★ **一次只插一块**：两块 2.8C 用的是**同一型号**的 USB 芯片 ⇒ PC 上出现两个同型号
> 设备，**靠端口号分不出谁是谁**。所以：插一块 → 烧 → 拔掉 → 再插另一块 → 烧 → 拔掉。

```powershell
# 仓库根目录（★ 中文路径下直接编会失败：ld.exe cannot open map file …Invalid argument
#  ⇒ 照 docs/RGB-PANEL-2.8C.md §14 的办法复制到纯 ASCII 路径再编/烧）

# ── ① 主板镜像：只插 A 板（右板）的 Type-C，看它是哪个 COM 口 ──
python -m platformio run -e esp32s3-rgb-master -t upload --upload-port COM6
#   （COM6 换成你机器上那个；两块板同时插着时**必须**显式指定 --upload-port）

# ── ② 拔掉 A 板的 Type-C，改插 B 板（左板）的 Type-C ──
python -m platformio run -e esp32s3-rgb-slave  -t upload --upload-port COM<n>

# ── ③ 两块板的 Type-C 都拔掉，然后按 §1 接线（43 交叉 + GND + 5V 只由 A 送）──
```

* ★ **先烧主板、后烧从板**（不是硬要求，但这样"接线前两块都已经是目标固件"）。
* ★ 烧完**不要**马上接链路：先确认 A 板那三个数字（见 §4 的判据），再接线。
* ★ **烧完的镜像里日志只走 19/20**（§2）⇒ **刷完串口上什么都不会出现**，那是正常的。
  想确认固件真的跑起来了，就用 `env:esp32s3-rgb`（不带链路 PHY 的那份）当"探针镜像"
  烧一次看开机那几行 —— 它和角色镜像**只差那两个 `-D`**（§5 的判据表）。

## 4. 判据：怎么算"通了"（贴什么日志）

> 下面这些行**全部在原生 USB-CDC（19/20）上**（§2）。从板只有插它自己的 Type-C
> 才能看见它那几行（代价：它同时从链路上掉下来）。

### 4.1 主板（A）上应当出现

```
206 dash ok
boot: ... prev=... prev_up=...            ← 既有那行（跨重启留档）
link: 主板侧就绪 TX=GPIO43 RX=GPIO44 @115200 8N1(§0/§1.1)      ← ★ 开机那一行，先看它
...
link: 首次收到从板帧(HELLO, role=0)                             ← ★ HELLO 互通
link: B HELLO fw=0 build=0 boot=0                               ← 从板报的版本/构建标记
link: B uptime=…ms rx_ok=… dropped=… crc=… gap=… face=… flags=0x00   ← 每 2 s 一行的 STATUS
link: tx=…B rx_ok=… crc=0 bad_len=0 unk=0 role=0   B 在线(对端已 …ms 没动静)   ← ★ 每秒那行
```

| 行 | 期望 | 它在证明什么 |
|---|---|---|
| `link: 主板侧就绪 TX=GPIO43 RX=GPIO44 @115200 8N1` | 一字不差 | §0/§1.1 的引脚与波特率**编译期**就对（没有"PHY 空壳"那句尾巴） |
| `link: 首次收到从板帧(HELLO, role=0)` | 出现 | ★ **B→A 上行真的通了**（v1 双向的那一半）—— 只接一根线时这一行**永远不会出现** |
| `link: B HELLO fw=… build=…` | 出现，且无"与本机 fw/build 不同"的尾巴 | 两块板是**同一份固件**（§3 的 HELLO 就是用来对账这个的） |
| `link: B uptime=…` 每 **2 s** 一行 | 频率 ≈0.5 Hz，`uptime` **单调涨** | `STATUS` 的 2 Hz 节奏对（§3 表 `0x30` 行）；`uptime` **反复归零** ⇒ 从板在反复重启（§7 失败模式 7：5V 带不动） |
| 每秒那行的 **`role=`** | **0** | ★ **角色冲突计数为 0** —— §5 ① 一次都没触发（不为 0 ⇒ 两块板刷了同一份镜像，见下） |
| 每秒那行的 **`crc=0` `bad_len=0` `unk=0`** | 全 **0** | 线上没有误码、帧长/类型表一致（不为 0 ⇒ 线太长/接触不良/共地不好/波特率不对） |
| 那行结尾 **`B 在线`** | 出现（30 s 内有过帧） | §8 L13 的 30 s 门限（**只进日志、不上屏**）—— `从板无响应` ⇒ 从板没上电/没刷/接线错 |

### 4.2 从板（B）上应当出现

```
link: 从板侧就绪(§5, LINK_ROLE=0) TX=GPIO43 RX=GPIO44 @115200 8N1 —— 真 PHY(UART0),等主板的 TICK/DATA
link: Locked tick_age=20ms seen=… seq_gap=0 miss=0 offset=…ms      ← ★ 每秒那行
SRC rpm=link speed=link coolant=link intake=link                    ← ★ 四个来源全变 Link
```

| 行 | 期望 | 它在证明什么 |
|---|---|---|
| `link: 从板侧就绪 … —— 真 PHY(UART0)` | 一字不差 | 从板**这一侧也带真 PHY**（本单的核心改动） |
| 每秒那行 **`tick_age`** | `TICK` 在到时 **≤ 约 60 ms**（50 Hz ⇒ 20 ms 一格） | 心跳在跑 |
| 每秒那行那个**状态词**（§4 的**三档**） | **`Locked`** | `>100 ms` ⇒ 变 `Lost`(失基准) / `>500 ms` ⇒ 降级 / `>3 s` ⇒ 回退 Sim —— 三档的名字就是判据 |
| 每秒那行 **`seq_gap=0 miss=0`** | **0** | `TICK.seq` 一帧没丢（丢帧 ⇒ 主循环被拖住或环溢出） |
| 每秒那行 **`offset=…ms`** | 一个**稳定**的负数/正数（不来回大跳） | §4 的偏移估计在工作（它只用于两屏相位对齐） |
| **`SRC … =link`** 四个字段 | 全部 `link` | ★ **数据走的是既有 `data_service` 的 `FieldSource::Link` 通道**（不是新造的通路）；`3 s` 收不到 `DATA` 会自然回退成 `sim`（§3 的 DATA 行） |
| 屏上左盘（转速 + 水温） | 跟着主板那台车的模拟数据动 | 端到端通了（**这是最终判据**：协议对不对，屏说了算） |

### 4.3 ★ 角色冲突（§5 ①）长什么样 —— 别去怀疑线

**症状**：主板那行 `role=` **不为 0** 且一直涨；`rx_ok`（`frames_ok`）**是 0**；
而 `crc=0`、`bad_len=0`、`unk=0` **一个都不动**。

⇒ 那说明**帧收到了、CRC 也过了**，只是 `frame_role == 本机 role` ⇒ 按 §5 ① 丢帧 + 计数。
**两块板刷了同一份镜像**（比如两块都刷了 `-master`），或者有一块的 `-DLINK_ROLE` 写错了。
改的就一处：重刷那一块（`master` ⇒ 1、`slave` ⇒ 0）。
★ 同一条判据在宿主机上也钉着：`test/test_dashcore/test_link_app.cpp` 的两个
`…role_conflict…` 用例（从板收从板帧 / **主板收主板帧**）与 `test_link_phy.cpp` 的帧层版本。

### 4.4 ★★ 台面上**不接 VAN 收发器**时，主板的 43/44 上跑的是什么（2026-09-25 实测）

这一条是拿着**逻辑分析仪级别的证据**写下来的（其实是直接读 UART0 的字节 + 解帧），
上台面之前先读它，免得把"设计如此"当成故障：

**现象**：主板镜像单独上电（没接从板、也没接 VAN 收发器）时，它的 43/44（= Type-C
那一对脚，此时归链路）上**一直在发东西** —— 二进制，不是文本。把它按 §2 的帧格式解出来：

| 实测（2026-09-25，COM6，3 秒窗口） | 读数 |
|---|---|
| UART0 上的字节率 | **36864 B / 3 s = 12288 B/s** = **115200 8N1 的满线速** |
| 解出的合法帧（`SYNC=0x5A`+`VER=0x10`+**CRC-15 逐帧校验通过**） | **2839 帧 / 3 秒** |
| 分类 | `HELLO` ×1、`TICK` ×52、**`DATA` ×2786** |
| 每一帧的 `ROLE` 字节 | 全是 **1（主板）** ✓ |

**为什么会这样（§3 的一条自记口径）**：`DataSender::due()` 对
**"本机一帧 0x824 都没收到过"**（`snapshot_ms == 0`：车睡着 / 台面上没接 VAN 收发器 /
VAN 那一路没启用）有一条**刻意的**"照发"口径 —— 它把 `now_ms` 当快照时刻
（"每次调用都是新的一份快照"）⇒ **主循环每一圈都能发一帧**。2.8C 上主循环 ≈900 圈/秒
⇒ `DATA` 就跑到 900+ 帧/秒。**这不是从板不在造成的**，也不能靠接线解决。

**现在的口径（2026-09-25 起）**：主板显式 `setMinIntervalMs(12)`（= 契约 §3 的
`DATA ≈ 79.7 Hz` 那一档）⇒ 这条路被压回 **≤80 帧/秒**。
- ★ 判据在宿主机上钉着：`test_link_app.cpp` 的
  `test_link_app_data_sender_min_interval_matches_contract_rate`（两个方向都测：
  ① 1 kHz 灌 ⇒ 输出 ≤84 帧；② 真实 0x824 的 12.5 ms 节奏 ⇒ **一帧都不丢**）。
- ★ 为什么这一条重要（不是"洁癖"）：满线速意味着 `pumpTx()` 每圈都顶在
  "FIFO 有位置"的边界上跑，正是 §1.2/§1.3 要避免的那种"把主循环拖住"的形态
  —— 而主板那一侧唯一有硬实时要求的是 **VAN 边沿采集**。
- ★ 有 VAN 的时候这条限速**不生效**（那时走"只有新的 0x824 才发"那一条，
  12 ms 的窗口对 12.5 ms 的到达率是透明的）。

## 5. 结果不对怎么查（按这个顺序，别跳）

1. **Type-C 拔了没有** —— 两颗板的都拔掉，43/44 才归 4Pin（§1 那颗 `FSUSB42UMX`）。
   这是**最常见**的一条：插着 Type-C 时链路必然不通，而且**不会有任何日志提示**。
2. **43/44 是不是交叉接的** —— `A.43 ↔ B.44`、`A.44 ↔ B.43`。用万用表通断档在**两头**
   各量一次（一根线两端都松的情况很常见）。
3. **GND 接了没有** —— 就一根，但少了它电平没有共同参考点。
4. **从板有电没有** —— A 板 12PIN 的 `5V` 对 GND 先量一次（§1 的注意 2）；
   从板屏亮不亮是最直接的判据（亮了说明 5V 那一路通）。
5. **看的是不是原生 USB 那个口** —— 链路固件在 Type-C（CH343P）上**一个字都不打**（§2）。
   拿 Type-C 看不到东西**不代表**板子没跑。
6. **`role=` 是不是 0** —— 不为 0 先看 §4.3，**别**去怀疑线、PHY 或分帧。
7. **`crc` 在涨但 `rx_ok` 也在涨** ⇒ 线上有误码：杜邦线太长/接触不良/**共地不好**；
   把线缩短、把 GND 那根加粗或就近接。
8. **主板报 `从板无响应`**（30 s）而上面几条都正常 ⇒ 从板那半条线（B→A）断了，
   或从板没跑起来（看它自己的口，§2 的办法 ①）。
9. **两边日志都对、屏上左盘不动** ⇒ 那已经不是链路问题了：看从板那行 `SRC …`，
   `4 个都是 link` 而屏不动 ⇒ 去查显示侧（`docs/RGB-PANEL-2.8C.md`）。

## 6. ★ 这套台面测试**测不到**什么（别把结论读过头）

**测到了**：
* §0/§1.1 的接线口径（43 发 / 44 收 / UART0 / 115200 8N1）在**两块真板**上跑通；
* 帧编解码 + CRC-15 + 重同步 + 大端字节序在**真实 UART 字节流、两条独立的板子**上站得住；
* **B→A 的上行**（`STATUS`/`HELLO`）真的通 —— 这是单板回环**测不到**的那一半；
* §5 的角色对账：**两块板各自报 `role_conflict`**，刷错镜像时能自证；
* §4 的三级超时在**真的断线**（拔线/拔 Type-C）时的表现；
* 非阻塞 PHY 在**真实主循环**（LVGL 在跑、每秒还在刷屏）里不被拖住。

**测不到**（说清边界）：
* **电气余量**：3.3 V 逻辑的噪声容限、线长上限、有没有振铃 —— 台面上没有示波器/眼图，
  `crc=0` 只说明"这一次连接、这一种线长"下没出错，**不是**"电气上永远没问题"；
* **车上的电磁环境**：点火、发电机、CAN/VAN 总线本身、大灯负载投切 —— 台面做不到；
* **43/44 的 L1 残余 ⓐⓑⓒ**（`ARCHITECTURE.md` §8 L1 那三条）：默认电平、44 对地电平、
  插上 Type-C 时链路"按预期失效" —— 台面流程只**用到**它们，**没有量**它们
  ⇒ 这三条的最小实测步骤单独写在 §7；
* **5V 支路的电流余量**（§8 L6 剩下那一半）：从板 + 480×480 背光峰值下那根 5V 的
  运行电流/峰值、刷机时会不会瞬跌 —— 要电流表；
* **中断密度对 VAN 采集的定量影响**（§8 L2）与**临界区最长允许多少**（§8 L3）：
  这两条要在**主板同时跑 VAN 硬实时**时才有意义 ⇒ 是**上车**的题，不是台面的题；
* **跨屏扫表对齐 < 40 ms**（§8 L5）：要两屏同拍（视频/拍照）才算；
* **链路长期稳定性**：台面跑几分钟到几十分钟只能证明"现在通"。

⇒ **两块板在台面上跑通**只说明"协议层 + PHY 层 + 角色对账在两块真板上成立"，
**不等于**"可以上车了"。

## 7. ★ §8 L1 残余 ⓐⓑⓒ 的**最小实测步骤**（万用表 / 直接试都能做）

这三条是 L1 关闭时**明确留下**的（原理图读得出来"二选一"，读不出"默认倒向哪边"）。

### ⓐ `SEL` 的默认电平（复位期间哪一路在 43/44 上）

**要什么**：万用表（直流电压档）+ 一块空跑的板子。

1. **不插** UART Type-C、**不接**任何排针线，只给板子供电（Type-C 供电也算 —— 但要注意
   "插了 Type-C"本身就会把开关切到 CH343P 那一边，所以这一步请**改用 12PIN 的 5V 供电**，
   这样才能观察"没有 Type-C 时"的默认状态）；
2. 万用表量 **12PIN 的 `GPIO0` 脚对 GND**：记下是接近 0 V 还是接近 3.3 V；
   （原理图上 `UART0SEL` 只有三个端子：`IO0` + `R44`/`R45` 两个 10 K ⇒ **`IO0` 上量到的
   就是那颗开关的 `SEL` 电平**。）
3. 再量 **12PIN 的 `RXD`（= GPIO44）对 GND**：这是 ⓑ 那一条（见下），两条一起量最省事；
4. 结论怎么写：`SEL` 高 ⇒ 43/44 接到 `HSD1±`（排针，4Pin 通）；低 ⇒ 接到 `HSD2±`
   （CH343P）。**把量到的电平与"哪一种"记进 `ARCHITECTURE.md` §8 L1 那一行**，
   这条残余就算收口。
5. 想看得更细（复位瞬间会不会抖）：有示波器就把探头挂在 `RXD`/`GPIO0` 上，按一下复位键，
   看那几十毫秒里有没有争用。**没有示波器就跳过**，把它写清"未测"。

### ⓑ 不插 UART Type-C 时 **44 对地电平**是不是干净的高

**要什么**：万用表 + 一个 1 kΩ 电阻（`ARCHITECTURE.md` §8 L1 原文口径：**串 1 kΩ 试**）。

1. 不插 Type-C、不接链路，量 **GPIO44 对 GND** 的空载电平（应当是接近 3.3 V 的**高**，
   因为 UART 空闲是高）；
2. 把 **1 kΩ 从 GPIO44 串到 GND**，再量 GPIO44 对 GND：电平应当**掉到接近 0 V**。
   ⇒ 说明那个脚是**真的被驱动着**（推挽输出/上拉够强），而不是悬空被漏电流抬起来的假高。
3. 反过来再试一次：**1 kΩ 从 GPIO44 串到 3V3**，量出来应当还是高（不塌）。
   ★ 这一步是为了排除"这个脚被另一路推挽顶着"（那就是 L1 当年担心的"对打"）。
4. ⓑ 的结论同时回答"能不能把 44 当输入"：**能收就是没人对打**（这正是 ⓑ 的目的）。

### ⓒ 插上 USB-C 再复测："链路**按预期失效**"

**要什么**：两块板按 §1 接好、链路已经跑通（§4 的判据全绿）。

1. 链路跑着的时候，**只给其中一块板**插上它的 UART Type-C；
2. 期望（这就叫"按预期失效"，**不是**"半死不活"）：
   * 那一块的 43/44 被切到 CH343P ⇒ **链路立刻断**；
   * 另一端走自己的降级路径：从板 `>100 ms` 失基准 / `>500 ms` 降级 / `>3 s` 回退 Sim
     （§7 失败模式 1）、主板 30 s 后那一行变 `从板无响应`；
   * **两块板的屏都不黑、都不重启**（"行车中断线不黑屏"那条口径）。
3. **不期望**看到的：`crc_err` 疯狂涨、`role` 计数涨、板子 brownout 重启、
   CH343P 那个 COM 口上出现一坨看不懂的二进制 —— 出现任何一条都说明
   "二选一"没按原理图那样工作，**要把现象原样记进 §8 L1**（那是新证据，别自己解释掉）。
4. 拔掉 Type-C ⇒ 链路应当**自动恢复**（`HELLO`/`TICK` 不用重启就回来，§7 失败模式 3）。

> ★ 这三条**都有替代做法**：真不想拿万用表，就只做 ⓒ（"直接试"）——
> 它能回答"到底通不通"；但 ⓐⓑ 那种"电平到底是多少"只有表能答，
> **别用"通了"去推"电平是干净的"**。

### 想回到"日志还在 Type-C 上"的那一档？

`env:esp32s3-rgb`（不带链路 PHY）就是那一档：日志/回放都在 43/44 = CH343P = Type-C 上，

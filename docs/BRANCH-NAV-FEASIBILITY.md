# 可行性研判：新分支「导航 + 转速」双屏（2026-11-21）

> 背景（车主）：整车改装过 —— 发动机、变速箱、行车电脑（ECU）、BSI 全换了。
> 目标形态：**左屏 = 高德导航（指针可自定义）**，**右屏 = 转速 + 进气温度**；
> 手动挡仪表自带独立水温表，所以水温不再需要。考虑**新开分支**开发。
> 本文只做研判（能做什么 / 难点在哪 / 要先定什么），不含代码改动。

---

## 0. 结论速览

| 项 | 判定 | 一句话 |
|---|---|---|
| 右屏 = 转速 + 进气 | ✅ **高可行，属小改** | 布局/主题层面就能改；真正的未知是**新 ECU 从哪给这两个数** |
| 左屏 = 导航（转向指针 + 距离等） | 🟡 **显示侧可行，数据侧是最大风险** | ESP32 跑不了高德；必须有中间设备把导航状态转成我们的短报文 |
| 指针可自定义 | ✅ **可行，但要动主题格式** | 两条实现路线（图片旋转 / 纯几何），需 R6 + 图片角色 24 |
| 中文路名/提示文字 | 🟡 **必须做字库工程** | 现在**只有 Montserrat**，中文一个字形都画不出来 |
| 新开分支 | ✅ **应该新开** | 改装后 **VAN 很可能没了（待你确认）**，现固件的"真值"几乎全来自 VAN ⇒ 这是重建数据源，不是打补丁 |

**一句话总结**：显示那一半（含指针、布局、字库）在现有架构里是"可控的增量"；
**导航数据从哪来、粒度多细**才是决定这项目值不值得做的关键，而它取决于你车上那台设备能给什么。

## 1. 改装之后：哪些还在，哪些死了

**还在（可直接复用，这些是过去几周攒下的资产）**

- 显示驱动（2.8C / ST7701S / 12 MHz / 双 framebuffer / bounce 30 行 / 局部刷新 43 Hz）
- 双板无线链路（ESP-NOW，实测 0% 丢包）与角色映射层
- 主题系统（16 KB 分区 + 编辑器 + 客户端 + 夜间模式 R5 + 指纹判据）
- 面板守护、复位原因落盘、OTA、日志环、native 用例（393 例）、落帧判据
- 图片资源分区（8 MB，零拷贝 mmap）

**死了（改装后基本可以认为不存在；★ 但值得你确认一句）**

- **VAN 解帧整条线**：车速、转速、水温、灯位、门、VIN 全部来自 VAN `0x824`/`0x4FC`/`0xE24`
  —— BSI 换了，推理上母线上不会再有这些帧。
  ★ 这是**推断**（按"BSI 换了 ⇒ VAN 也没了"），不是实测：**如果新 BSI 居然还在跑 VAN，
  那反而是好消息**（现成的解帧、灯位、VIN 全都能继续用）。所以这一条请顺手确认。
- 由车速/转速派生的"表情档位""超速红区""数据可信"判据（依赖 VAN 新鲜度）
- 仪表里的红区/断油参考值（新发动机的断油点未知）

**半死的（要重新确认）**

- **K 线 OBD-II**：新 ECU 是否还提供 `010C`（转速）/`010F`（进气）？这是右屏的全部数据来源。
- 若有 **CAN**：S3 内置 TWAI，配上手上那块 SN65HVD230 收发器就能收 —— 但需要新写驱动与解析。

> ⚠️ 现在固件在 VAN 缺失时会**自动退化到 OBD → Sim**（现成机制，不用改），但那只是"不黑屏"，
> 不代表有真值。

## 2. 逐条可行性

### 2.1 右屏：转速 + 进气（工作量最小）

- UI 侧：主题里把该屏的弧改成"转速外弧 + 进气内弧"，读数位置照旧 ⇒ **改主题即可**，固件可不动。
- 数据侧：见 §1，取决于新 ECU。
- 风险：转速量程/红区要按新发动机重定（`AlertsConfig.redline_rpm`、`kRpmMax`），否则红弧和断油对不上。

### 2.2 左屏：导航显示（显示侧可行）

现有主题体系是"**弧 + 表情 + 读数**"的表盘形态。导航页是**另一种布局**，建议在主题里加
`screen.layout = "dial" | "nav"`，而不是把导航硬塞进弧里。导航页要画的元素大致：

| 元素 | 难度 | 说明 |
|---|---|---|
| 转向指示（大箭头/指针） | 🟢 | 位图随 `turn_type` 换图，或单张图旋转 |
| 到路口距离 | 🟢 | 数字 + 单位，现成的 readout 机制可复用 |
| 路名 / 下一条指令 | 🟡 | **中文**，见 §2.4 |
| 车道 / 限速 / ETA / 进度条 | 🟡→🟠 | 看你要到哪个程度，每加一项就多一套素材与协议字段 |

### 2.3 指针自定义（两条路线，建议都留）

| 方案 | 外观自由度 | 开销 | 现状 |
|---|---|---|---|
| **A. 图片指针**（`lv_image` + `set_rotation`/`pivot`） | 高（自己出图） | 每帧做图像变换：CPU/带宽比弧贵；需确认 LVGL 变换开关已编进去 | `lv_image_set_rotation` **在用的 LVGL 里有**；`lv_conf.h` 没显式开变换开关（走默认值） |
| **B. 几何指针**（细弧/线段 + 角度映射） | 中（形状靠参数） | 最省，和现在 43 Hz 局部刷新同一量级 | 现成弧机制可复用 |

建议：**主题里加 `needle.style = "image" \| "geometry"`**，先做几何（快、稳），图片作为增强。
新增主题键（**R6**）：`needle{style, length, width, color, pivot_x/y, angle_from, angle_to, reverse, image_role}`；
新增图片角色 **24 = Needle**（480×480 内任意尺寸，靠 pivot/角度映射摆位）。
判据：落帧对角度映射逐点比对 + 盯 `inv=`（每秒脏区）看旋转开销。

### 2.4 中文：现在画不出来（容易被低估）

`include/lv_conf.h` 里只使能了 **Montserrat 10/14/18/24/48**，没有任何中文字库
（`dash_role_layout.h` 的注释也写明"本构建只使能 Montserrat，中文一个字形都画不出来"）。

导航要显示"**前方 300 米 右转 · 中山路**"这种文本 ⇒ 必须：
1. 用 `lv_font_conv` 生成**常用字子集**（GB2312 一级 3755 字，2 bpp 约 1~2 MB，放 flash；flash 有 15 MB 余量）
2. 主题/编辑器支持"字体档位"（现在只有 `digit_font/unit_font/sub_font` 三个枚举，要扩到含中文档）
3. 注意 RAM：LVGL 字体是只读的（放 flash 不占 RAM），但**首帧字形缓存**与绘制路径要实测

**这是我认为除数据源外第二大的活儿**，且必须在做"导航页"之前定下（否则路名只能显示拼音/英文）。

### 2.5 布局/角色重排

现在角色映射是硬编码的（`dash_role_layout.h`：`LINK_ROLE==1 ⇒ 主题 index 1 = 速度表`，
从板 ⇒ index 0 = 转速表）。新形态是"**右板 = 引擎，左板 = 导航**"：

- 需要把 `roleThemeIndex()` 从"常量"改成"**角色 → 屏内容**的映射表"（含 nav/dial 类型）
- 现有 `static_assert` 与 `test_role_layout_*` 用例要跟着改（它们是防止"屏串了"的护栏，不能丢）
- 好消息：**主题侧的 `kScreenCount=2`、每屏弧/读数/图片角色的机制不用动**

## 3. 导航数据怎么进来（最关键、也最不确定）

**现实**：ESP32 不可能跑高德；高德也没有"把实时导航指令推给第三方硬件"的公开接口。
所以必须有个**中间人**（手机/Android 车机/盒子），我们只负责"收短报文 → 画"。

| 路线 | 可行性 | 代价 | 备注 |
|---|---|---|---|
| **A. Android 侧桥接 App**（推荐） | 🟡 取决于拿数据的合法性 | 要在车机上装 App；拿数据的方式决定成败 | 两条子路：①自己用**高德 SDK** 起导航（合规、可控，但那就不是"用高德 App 导航"）；②监听高德车机版的广播/无障碍服务（民间常见，属灰色，版本升级就可能断） |
| B. CarPlay / Android Auto 的 cluster 扩展 | ❌ | 需要车厂认证 | 个人项目不可行 |
| C. 自研离线导航 | ❌（对我们） | 等于重做一个导航 | 地图+路径规划+路况，不现实 |

**传输层选型**（我们有现成经验）

| 通道 | 优点 | 缺点 |
|---|---|---|
| **BLE**（NimBLE，NUS 风格） | 已在用（BLE OBD），有 `radio_arbiter` 共存策略 | 与 ESP-NOW/BLE OBD 抢射频；要排优先级 |
| WiFi（STA + TCP/UDP） | 带宽大、协议自由 | SoftAP 会切信道打断 ESP-NOW（`ota_wifi.h` 里写明了）；需要热点或手机开热点 |
| USB 串口 | 最稳、零射频冲突 | 多一根线；车机需支持 USB 主机/OTG |

**建议**：先按 **BLE 短报文** 设计（字段少、频率低：导航指令变化才发，1~5 Hz），
把 `nav_source` 做成**协议适配层**，将来换 WiFi/串口只换传输、不动 UI。

**协议草案（极简，够画导航页）**：`turn_type(0..15)`、`dist_m(0..2559)`、`road_name(可选,UTF-8)``、
`speed_limit`、`eta_s`、`progress_0..100`、`seq`、`crc`。≈ 24~48 字节一帧。

## 4. 建议的分支与代码结构

- 分支：`feat/nav-cluster`（从 `main` 切，`main` 保留 VAN 老车那条线）
- 环境：新增 `esp32s3-rgb-{master,slave}-nav`（`-DDASH_MODE_NAV=1`），**不动现有两个 `-now` env**
- 新增模块（都不碰老代码路径）：
  - `lib/dashcore/nav_state.h`（纯数据 + 超时/降级/校验，native 可测 —— 与 `night_mode.h` 同风格）
  - `lib/dashcore/nav_source_ble.{h,cpp}`（传输适配，先 BLE）
  - `src/nav_ui.cpp`（导航页：指针 + 距离 + 文字）
  - 主题 R6：`screen.layout`、`needle{…}`、中文字体档；图片角色 **24 = Needle**
  - 链路新消息 `0x22 NAV`（**仅当**导航数据落在一块板、要显示在另一块时才需要）
- 数据源：新 ECU 若走 CAN ⇒ 加 `twai` 驱动 + 新 `CanSource`；若仍有 OBD-II ⇒ 直接复用 `obd_source`

## 5. 风险清单（按严重度）

1. ★★★ **导航数据拿不到 / 粒度太粗**（只能拿到"还有多少米"、拿不到"右转/左转/掉头"）⇒ 指针无意义
2. ★★☆ **中文字库**（体积、字体档、编辑器、首帧绘制开销）—— 容易被当成"小事"，实际是独立工作量
3. ★★☆ **新 ECU 的接口未知**（CAN 私有帧？OBD 还在不在？有没有协议文档）⇒ 右屏能不能做的唯一前提
4. ★★☆ **布局重构**：主题从"表盘"扩成"表盘/导航"两种形态，编辑器也要跟
5. ★☆☆ **指针渲染开销**：图片旋转每帧做变换，需实测 `inv=` 与 CPU 余量（弧那条路已验证）
6. ★☆☆ 双板链路：若导航只显示在左板（BLE 直连左板），可能**不需要**新链路消息
7. ★☆☆ 表情还要不要？"表情代替指针"是这个项目的灵魂，新形态里左屏是导航、右屏是转速表 ——
   **右屏留表情、左屏不留**大概是最自然的取舍，但要你定。

## 6. 要你先回答的 6 件事（决定方案与工作量）

1. **新 ECU/BSI 的数据出口**：诊断口还在吗？是 OBD-II（K 线/CAN）还是私有 CAN 帧？有没有文档/协议表？
2. **导航数据从哪台设备来**：Android 车机 / 手机 / CarPlay 盒子？能不能在它上面跑自研 App？

5. **右屏是否还要车速**？（原车仪表有车速表吗）导航页要不要顺带一个车速数字？
6. **双板保留吗**（左=导航、右=引擎），还是合并成一块？

## 7. 不等答案也能先做的一步

## 8. ⚠️ 一个环境前置问题（今天实测，与本议题无关但会挡住开发）

这台机器现在**跑不了构建**：PlatformIO 要写 `C:\.platformio\platforms.lock`，而当前 shell 沙箱
只允许写工作区（实测：`C:\206dash-scratch`、`C:\temp`、`C:\206dash-build`、`C:\.platformio` 全部 `Permission denied`，
只有 `C:\Users\张九思\206Dash` 可写）⇒ `pio run` 直接 `PermissionError`。

**开始新分支前必须先解决**：把工具权限改成能写这些目录（或允许 full access），
否则连"编一次固件"都做不到。参考数值（上一轮正常构建时的占用，用于判断余量）：
内部 RAM **48.7%（159 KB / 320 KB）**、Flash **8.9%（1.49 MB / 16 MB）**、PSRAM 剩 **7,282 KB**。

# 第二部分：车主回答之后（2026-11-21 晚，方案收敛）

## 9. 车主的 6 个回答 → 结论

| 问题 | 回答 | 对我们的意义 |
|---|---|---|
| 数据出口 | **诊断口还在；协议没变**（行车电脑只是 **ME7.4.4 → 7.4.5**） | ★ 好消息：**K 线 EOBD 还在** ⇒ 转速 `010C`、车速 `010D`、进气 `010F` 都能读（ME7.4.x 是 K 线 ISO 14230，见 [BOSCH ME7.4.4/EOBD 说明](https://cargeek.live/docs/citroen_bosch_ME7.4.4_operating_principle.pdf)）。之前用 BLE ELM327 实测过 `010D`（车速标定就是它标出来的），所以这三个 PID 大概率通 |
| 导航来源 | **小米 14（Android）+ 高德手机版**，可以跑自研 App | 走**社区成熟路线**：高德发出的标准广播 `AUTONAVI_STANDARD_BROADCAST_SEND` → 我们的 App 收 → BLE 给 ESP32 |
| 左屏要什么 | 参考已有方案 | 已有方案基本是：**转向箭头 + 到路口距离**（+ 车速/ETA/路名） |
| 指针边界 | **图片指针**，指代车辆在导航屏上移动 | 车图标（图片）随 `CAR_DIRECTION` 旋转；★"**移动**"见 §11 的取舍 |
| 右屏车速 | 可以加 | 右屏 = 转速 + 进气 + 车速（车速数字从 OBD `010D` 或从板间链路来） |
| 双板 | 保留 | 左 = 导航（BLE 中央），右 = 引擎（OBD），ESP-NOW 继续连 |

## 10. 收敛后的数据通路

```text
【右板 · 主板】 OBD K 线（ME7.4.5, ISO14230）
   010C rpm / 010D 车速 / 010F 进气 ──> DataService ──> 右屏（转速弧 + 进气 + 车速数字）
                                   └──> ESP-NOW DATA ──> 左板（导航页显示车速）

【左板 · 从板】 BLE 中央（复用现有 NimBLE + radio_arbiter）
   ←── 小米 14 上的自研 App（监听高德广播 AUTONAVI_STANDARD_BROADCAST_SEND）
   ──> nav_state（纯数据）──> 左屏（箭头 + 距离 + 车图标 + 路名/ETA）
```

- **VAN 解码整条线停用但代码保留**（万一新 BSI 还在发 VAN 就能复活；也保住历史判据）。
- OBD 两条路都可行：**继续用 BLE ELM327 头**（零改动、已验证）或**改有线 K 线**（VAN 不用了 ⇒
  `GPIO43/44` 空出来了，可以挂 L9637D 直接读）。建议**先保持 BLE 头**（确定性高），有线作为后续优化。
- 每块板都只有 **1 个 BLE 角色 + ESP-NOW** ⇒ 与现在"主板 BLE-OBD + ESP-NOW"是同一个共存问题，
  `radio_arbiter` 的策略可直接搬。

## 11. ★ 一个必须先讲清楚的取舍：「车图标在屏上移动」

高德**广播**给的是"转向图标 / 距离 / 路名 / 车速 / 车头方向"，**不给路线几何**。所以：

| 做法 | 能不能"移动" | 代价 |
|---|---|---|
| **A. 只用广播**（推荐先做） | ❌ 车图标**居中、只旋转**（跟随 `CAR_DIRECTION`）；箭头/距离/路名在变 | 一个 Android App 监听广播 + BLE 推 → 简单、稳 |
| **B. 自研 App + 高德 SDK 导航** | ✅ 能拿到路线点，做 heading-up 滚动地图，车图标真的在地图上走 | App 要自己跑导航（不是"用高德 App"），需要 SDK Key；ESP32 侧要画路线/建筑（参考 [moto-gps-waveshare 的 BLE Navigation v1](https://github.com/mx3353672833-debug/moto-gps-waveshare/blob/main/shared/protocol/ble-navigation-v1.md)，它就是这么做的：手机出路线点，ESP32 只渲染） |

建议：**A 先落地**（1~2 天就能看到东西），**B 作为第二阶段**（如果 A 看着不够"导航感"再上）。

## 12. 高德广播的字段（社区方案已解析，可直接照抄）

动作：`AUTONAVI_STANDARD_BROADCAST_SEND`

| KEY_TYPE | 含义 | 我们需要的字段 |
|---|---|---|
| `10001` | 导航/巡航 | `NEW_ICON`/`ICON`（转向图标）、`SEG_REMAIN_DIS_AUTO`（到路口距离）、`CUR_SPEED`、`NEXT_ROAD_NAME`/`CUR_ROAD_NAME`、`ROUTE_REMAIN_TIME_AUTO`、`ETA_TEXT`、`LIMITED_SPEED`、**`CAR_DIRECTION`**（车头方向）、`ROUTE_REMAIN_DIS` |
| `10019` | 昼夜 | `EXTRA_STATE`（37 白天 / 38 夜晚）⇒ **可直接驱动我们的夜间模式**，不用再靠车灯 |
| `60073` | 红绿灯倒计时 | 可选（很"导航"的一个噱头） |
| `13012` | 车道线 | 可选（阶段 B） |

**转向图标编号（社区实测）**：`2` 左转 · `3` 右转 · `4` 左前 · `5` 右前 · `8` 掉头 · `9` 直行 ·
`10` 途经点 · `11` 进匝道 · `12` 出匝道 · `15` 终点。⇒ 我们只需 **9 张箭头图**（图片角色）。

## 14. 风险清单（更新后）

1. ★★★ **高德手机版当前版本还发不发这条广播**（社区方案可能跟的是老版本）⇒ **先花 10 分钟验证**，
   这是整个项目唯一的 go/no-go。
2. ★★☆ 小米 14（HyperOS/Android 14+）的后台限制：接收 App 必须前台服务 + 电池白名单，否则导航一会儿就断。
3. ★★☆ 新 ECU 的 K 线是否真的还答 `010C/010D/010F`（ME7.4.4→7.4.5 版本变了，PID 支持位图可能变）⇒ 上车前用 ELM327 先扫一遍。
4. ★★☆ BLE（导航）+ ESP-NOW（板间）共存：沿用现有 `radio_arbiter`，但要实测导航推送 2~5 Hz 下的链路质量。
5. ★★☆ 若走阶段 B：中文字库体积/首帧开销 + 路线渲染的 CPU（43 Hz 局部刷新下画曲线要量 `inv=`）。
6. ★☆☆ 车图标"移动"需要路线几何（广播给不了）⇒ 阶段 A 只能居中旋转（已在 §11 说清）。

## 15. 不用写固件就能先做的两件验证

1. **广播验证**：小米 14 装一个"广播监听"App（或 20 行 Android 小工程）→ 打开高德导航 →
   看 `AUTONAVI_STANDARD_BROADCAST_SEND` 的 `KEY_TYPE=10001` 是否来、字段是否齐（图标/距离/路名/heading）。
   **这一步过了，整个方案就成立。**
2. **ECU 验证**：现有 BLE ELM327 头插上，读 `010C`、`010D`、`010F`，看是否答（以及支持位图 `0100`）。

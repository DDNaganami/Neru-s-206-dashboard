# 抄这两个方案的结论（2026-11-22，车主指定参考）

参考：
- `mx3353672833-debug/moto-gps-waveshare` —— 手机出**路线点 + 可选的"离线道路/建筑滚动窗口"**，
  ESP32 只做**矢量渲染**（BLE 协议 v1，一帧 1.3~2.2 KiB）
- `zuo-qirun/Amap-for-ESP32` —— 手机转发**高德车机版广播**，聚合成**完整 JSON 快照**，走 **Wi-Fi UDP**，
  ESP32 端 128×64 OLED 文本/图标显示

## 结论：两条都不发图片

| | 数据形态 | ESP32 干什么 | 带宽 |
|---|---|---|---|
| moto-gps-waveshare | 路线点 + 道路/建筑折线点（压缩） | 画折线（heading-up） | ~1-2 KiB/帧 |
| Amap-for-ESP32 | JSON 快照（图标/距离/车道/红绿灯） | 文本 + 图标 | 数百字节/帧 |
| **我们之前的 JPEG 画中画** | 整张 240×240 JPEG | 解码 + 贴图 | 7-12 KB/帧（且解码卡住） |

⇒ **JPEG 那条路是过度设计**，而且正好卡在 LVGL 解码器上。
**正确做法 = moto 的矢量地图窗口**：手机把"车前方 200~400 m 内的道路折线"（可以只取高德路线本身
+ 少量并行道路）按车体坐标压成点列发过来，板子用 `lv_draw_line` 画——这正是我们已经跑通的 `0xA8` 路线帧的
**多折线扩展版**，不需要任何图片解码。

## 立即切换的施工单（替代 docs/NAV-MAP-PIP.md 的图片方案）

1. **协议扩展（0xAA = 地图窗口）**：一帧携带 N 条折线，每条 `{点数, 点列(dx,dy i16)}`，
   N≤8、总点数≤96（≈ 400 B/帧），沿用现有 CRC16 与分片机制
2. **App**：从 `AMapNavi.getNaviPath().getCoordList()` 取路线点（已有），
   另加 **`aMap.getMapScreenShot` 之外的道路数据**：最简单先只发"路线本身 + 路口的转弯点"，
   即把现有 0xA8 扩成"多段线"；后续要更像地图再加并行道路（高德 SDK 的 `AMap.getMapContentApproval` 拿不到，
   可用 SDK 的 `AMapNaviPath` 只画主路线）
3. **固件**：`nav_map` 模块解析多折线 → 在 360×360 区域内按 heading-up 旋转绘制
   （外描边 + 内亮线 + 路口圆点 + 车标），**删除 map_poll/JPEG 解码那一整段**
4. **保留**：现有的横纹治理参数（弹跳 40 / 停广播 / 60~90ms / -12dBm）

## 为什么这样更快

- 没有解码器、没有 PSRAM 图像缓冲、没有 7-12 KB 大帧
- 与我们已跑通的东西只差"一帧多条折线"
- 视觉上：黑底上有多条道路折线 + 高亮路线 + 车标，已经接近"画中画"的观感
